# clicksend after 1.0.0: audit, research and roadmap

Status: working design for the next minor release, written 2026-10-06 on branch `next/1.1`.
1.0.0 (tag `v1.0.0`, commit `d460f9e`) is not modified.

Principle: **the official SDK wins on breadth; clicksend wins on correctness, ergonomics,
safety and Ruby developer experience.** Nothing here turns clicksend into a second generated
SDK.

## 1. Evidence

Labels used below: **documented** (schema or prose), **archived** (only in superseded docs),
**observed** (our live runs, 2026-10-05), **undocumented**.

### 1.1 Facts that drive the design

1. **No idempotency key anywhere** (documented by absence; grepped all 34 specs). The only
   related mechanism is the application code `THROTTLED`: "Identical message body recently sent
   to the same recipient". Its window and placement are undocumented, so it is not a dedup
   guarantee and the gem must not rely on it.
2. **History is the only documented reconciliation path** after an ambiguous send:
   `GET /v3/sms/history` with `date_from`, `date_to`, `order_by`, `page`, `limit` and one
   `q=field:value`, where the documented fields are `status`, `to`, `from`, `subaccount_id`
   and `message_id`. **`custom_string` is not a documented filter**, so matching on it is
   client-side. Whether history is immediately consistent after a send is undocumented: an
   absent row is *not* proof that a message was not sent.
3. **Webhooks ("push") exist only as automation rules with the `URL` action.** Inbound rules
   take `webhook_type` `post` (default, form-encoded), `get` or `json` (the JSON format is
   unspecified). Receipt rules have no format option; help article 42270 says form-encoded.
   The current docs define **no push payload schema**; the archived v3 docs list the fields,
   which match the current poll schemas (`sms_receipt`, `inbound_sms`) plus `user_id` and, on
   receipts, `status` ("Delivered"/"Undelivered"). Archived: ClickSend retries a non-200 every
   10 minutes, 10 times.
4. **Webhooks are not signed or authenticated.** No HMAC, signature header, shared secret or
   published IP ranges in any current, archived or help source. A push can be forged. The gem
   must not pretend otherwise.
5. **Rate limits are undocumented** beyond status 429 (whose "See Rate Limiting" link points
   nowhere). Observed headers: `x-ratelimit-limit`, `x-ratelimit-remaining`, `ratelimit-reset`
   (seconds), and `Retry-After` on 429, all on `GET /v3/account`.
6. **No request ID or correlation header** is documented.
7. **Mark-read with no cutoff marks everything read** (documented in prose and an archived code
   comment). There is no per-receipt mark-read endpoint.
8. **Test numbers never produce delivery receipts** (legacy v2 docs). Our live receipt gap was
   expected behaviour.
9. `POST /v3/sms/price` has no *stated* side effects, but none are ruled out either, and its
   example returns a `message_id`. `PUT /v3/sms/cancel-all` with an empty body cancels **every**
   scheduled message.

### 1.2 What the official SDK (clicksend_client 6.0.2) does

Better: breadth (175 operations, 26 API classes), typed request/response models, maintained by
ClickSend from its own spec, Ruby 2.7+, client certificates and file downloads.

Worse, each verified in its source:
- `timeout = 0` ("never times out"); no connect timeout (libcurl default ~300s)
- no retries, no backoff, no `Retry-After` handling
- a single `ApiError` for everything, whose message embeds full headers and body
- HTTP 200 sends with refused messages are not detected
- mutable global configuration singleton
- unknown response fields dropped, no raw payload
- debug mode prints the `Authorization` header and bodies
- redirects always followed
- no pagination, webhook, instrumentation or testing support
- the 6.0.2 `.gem` is 9.7 MB because it ships a vendored bundle

## 3. Feature decisions

Each feature answers: API support · honest semantics · value · fit · maintenance · coupling ·
placement · complexity · maintenance cost · developer value.

### P0 (target 1.1.0)

**3.1 Error context and explicit ambiguity**
- Support: needs nothing from ClickSend. Semantics are the gem's own retry classification.
- `Error#request` → `Clicksend::RequestInfo(method, path, operation, idempotent, attempts)`.
  The path never includes the query string.
- `Error#retryable?`: repeating the same request later is safe *and* may succeed. True for 429;
  for connection failures that never reached ClickSend; and for connection failures and 5xx
  on idempotent requests. False otherwise, including every ambiguous error, 4xx,
  `MessageRejected` (a `THROTTLED` rejection means an identical message was just sent) and
  malformed responses.
- `Clicksend::AmbiguousRequestError` is a **module** extended onto the raised error when a
  non-idempotent request may have been processed: a connection failure that may have been
  sent, a 5xx, an error reported inside a 2xx body, or an unreadable 2xx response. The error
  keeps its class (`TimeoutError`, `ServerError`, ...), so existing `rescue` clauses still
  work, and `rescue Clicksend::AmbiguousRequestError` catches every unknown-outcome failure.
  `Error#ambiguous?` is the predicate.
- Not named "AmbiguousDeliveryError": the uncertainty is whether ClickSend *accepted* the
  message, not whether it was *delivered* (receipts report delivery).
- Rejected: `clicksend_code` (alias of `response_code`; aliases add surface without meaning),
  `request_id` (none documented).
- Placement core; complexity low; maintenance low; value high.

**3.2 Retry and rate-limit refinements**
- The safety rule moves from `RetryPolicy` into `Connection`: a request is eligible for retry
  only when it is a real HTTP 429, a connection failure that never reached ClickSend, or (for
  idempotent requests only) a connection failure or real 5xx. The policy only decides *how
  long* to wait and *whether the budget allows it*. A custom policy therefore cannot make an
  ambiguous send retry.
- `Clicksend::RetryPolicy` becomes public: `RetryPolicy.new(max_retries: 2, base_delay: 0.5,
  max_delay: 8.0, max_retry_after: 30)`, passed as `Client.new(retry_policy:)`. Any object with
  `max_retries` and `delay(error:, attempt:)` works. `max_retries:` stays as the shortcut.
- **Bug fix:** `mark_receipts_read` / `mark_inbound_read` without `before:` mark everything
  read *as of the moment ClickSend processes them*. A retry after an ambiguous first attempt
  could mark items read that arrived in between and that the caller never saw. Those calls are
  now idempotent only when `before:` is given.
- `Clicksend::RateLimit(limit, remaining, reset_in, reset_at)` parsed from the observed headers
  and exposed as `Response#rate_limit` and `APIError#rate_limit`. It is nil when the headers
  are absent, and documented as observed, undocumented behaviour.
- `Response#request` carries the same `RequestInfo`, including `attempts`.
- Placement core; complexity low; maintenance low; value high.

**3.3 Instrumentation**
- `Client.new(instrumenter:)` accepts any object with
  `instrument(name, payload) { |payload| ... }`, which is `ActiveSupport::Notifications`'
  signature, so Rails apps pass `ActiveSupport::Notifications` with no adapter and no
  dependency.
- Events:
  - `request.clicksend` wraps one logical call, including retries. On completion its payload
    holds `method`, `path`, `operation`, `idempotent`, `attempts`, `http_status`,
    `response_code` and `ambiguous`.
  - `retry.clicksend` fires for each scheduled retry, with `method`, `path`, `operation`,
    `attempt`, `delay`, `error_class` and `http_status`.
- **Never emitted:** credentials, headers, query strings, request or response bodies, phone
  numbers, message text.
- Placement core; complexity low; maintenance low; value high (it is how production teams
  see retries and rate limiting).

**3.4 Testing support: `require "clicksend/testing"`**
- `Clicksend::Testing::FakeAPI` is an in-memory, thread-safe ClickSend implemented as a
  *transport*. Applications use a real `Clicksend::Client` with it, so validation, error
  mapping, retries and models are the production code paths.
- It records accepted messages and every request. It can reject per recipient, inject
  failures (refused, timeout, reset, any HTTP status) **with an explicit `processed:` flag**
  for ambiguous failures, seed receipts and inbound messages with ClickSend's mark-read
  semantics, serve history, and stub any other endpoint.
- Not loaded by default. It does no I/O. Usable as a development "dry run" transport, which is
  why there is no `dry_run:` flag.
- Placement core (opt-in file); complexity medium; maintenance medium (it must track the
  wrapped endpoints only); value high.

**3.5 Webhook parsing: `Clicksend::Webhook`**
- `Webhook.parse_receipt(params)` → `SMS::Receipt`; `Webhook.parse_inbound(params)` →
  `SMS::InboundMessage`; `Webhook.parse(params)` detects the type and raises
  `Webhook::InvalidPayload` when it can't tell. Parses form, query or JSON params already
  decoded by the web framework (a Hash, string or symbol keys, or Rails parameters).
- **No verification method**, because ClickSend provides nothing to verify. The docs prescribe
  an unguessable secret in the URL, HTTPS, idempotent handling on `message_id`, answering 200
  fast, and confirming anything consequential with `sms.receipt(message_id)`.
- The field names come from the current poll schemas and the archived push docs, and the two
  agree. The README says the push format is not in ClickSend's current docs.
- Placement core; complexity low; maintenance low; value medium to high.

**3.6 SMS history (the reconciliation path)**
- `sms.history(date_from:, date_to:, to:, from:, status:, message_id:, order:, page:, limit:)`
  → `Page<SMS::HistoryRecord>`.
- At most one of `to:`/`from:`/`status:`/`message_id:`, because one `q=field:value` is the
  documented form; the combination operator for several is undocumented.
- The README documents reconciliation after an ambiguous send, and states that an absent row
  is not proof of non-delivery.
- Placement core; complexity low; maintenance low; value high (it completes the
  ambiguous-send story).

**3.7 Documentation**
- Positioning: when to use the official SDK, clicksend, or the escape hatch.
- Reliability semantics: ambiguity, retries, 429, rate limits, errors.
- Testing, webhooks, observability, and an ActiveJob recipe.
- API notes updated with this research.

### P1 (target 1.2.0)

- **OpenTelemetry**: `require "clicksend/opentelemetry"` gives an instrumenter that opens a
  client span per logical call, with retry events, using the OTel API gem if the application
  has it. Soft dependency, no gemspec change. Deferred because its value depends on the
  instrumenter API settling first.
- **Cancel one scheduled message**: `sms.cancel(message_id)`. Idempotent in intent; a second
  call's behaviour is undocumented, so contract-test it and live-verify it on a scheduled
  test-number message first. **Reject `cancel-all`** as a wrapped method: an empty body cancels
  every scheduled message account-wide.
- **Price quote**: `sms.quote(...)` over `POST /v3/sms/price`. Treated as non-idempotent until
  ClickSend states it has no side effects or the owner approves a live check.
- **Persistent connections**: document `adapter: :net_http_persistent` and add a send-safety
  test for it (it must not retry POSTs on a stale connection).

### P2 (optional ecosystem)

- `clicksend-rails`: credentials lookup, an ActiveJob delivery job that encodes the retry rules
  (`retry_on` only for `retryable?`, discard and report on ambiguity), and test helpers wired to
  `FakeAPI`. A separate gem, so the core never depends on Rails.
- RSpec matchers over `FakeAPI` (e.g. `have_sent_sms(to:)`).

### Rejected

| Idea | Why |
|---|---|
| Automatic retry of ambiguous sends | The founding rule: a duplicate SMS is not recoverable |
| Automatic "reconcile then resend" (`deliver(reconcile: true)`) | History consistency is undocumented, so "not found" cannot prove "not sent"; it would be false safety |
| Relying on `THROTTLED` as deduplication | Window and placement undocumented |
| Webhook signature verification | ClickSend provides none; inventing one would be security theatre |
| `dry_run:` flag | A transport already does this without branching the client |
| Client-side rate limiter / token bucket | Limits are undocumented and appear per endpoint and source address |
| Per-receipt mark-read | No such endpoint |
| A "mark read after processing" helper | The only cutoff is a timestamp, which can cover unseen same-second receipts |
| Global configuration singleton | It undermines the frozen, per-instance client |
| Wrapping more of the API or generated models | That is the official SDK's job |
| Rails engine in the core gem | Coupling; see P2 |
| CLI | Sending SMS from a shell adds risk, not value; `client.account.fetch` in a console already checks credentials |
| SMS part/cost estimator | ClickSend's own length rules are inconsistent (help 42194) and Unicode depends on an account setting; `POST /v3/sms/price` is authoritative |

## 4. Architecture of 1.1

```
Client (frozen)  ── resources: sms, account (operation names: "sms.deliver", ...)
  │  request(method, path, query:, body:, idempotent:, operation:)
  ▼
Connection
  ├─ instrumenter.instrument("request.clicksend", payload) { attempts loop }
  ├─ classify(error) → retry-eligible?           ← safety invariant (not configurable)
  ├─ retry_policy.delay(error:, attempt:)        ← timing and budget (configurable)
  ├─ marks AmbiguousRequestError, attaches RequestInfo, RateLimit
  └─ transport.call(...)                          ← Faraday (default) | Testing::FakeAPI | custom
Webhook (pure functions over params) ─► SMS::Receipt / SMS::InboundMessage
Testing::FakeAPI (opt-in file) implements the transport interface
```

Invariants preserved: Ruby >= 3.3, Faraday 2 the only runtime dependency, the `Clicksend`
namespace, frozen thread-shareable client, no redirects, HTTPS-only `base_url`, path
validation, no credentials in output, conservative retries.

## 5. Release plan

- **1.1.0**: everything in P0. Additive, except the mark-read retry fix and error messages that
  now name the method and path.
- **1.2.0**: P1 (OpenTelemetry, cancel, quote after verification, persistent connections).
- **Companion gems**: `clicksend-rails` (P2), only if there is demand.
