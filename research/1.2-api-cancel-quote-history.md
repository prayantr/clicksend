# 1.2 spike: `sms.cancel`, `sms.quote`, history after an ambiguous send

Track B, part 2 (B3, B4, B6). Branch `spike/1.2-api`, from the 1.1.0 release commit `7e96b24`.
Written 2026-10-06. **No ClickSend API call was made**: no credentials were used, nothing was
sent, cancelled or priced. Only public documentation was read.

Founding invariant: *a missed retry is recoverable; a duplicate SMS is not.* Nothing below turns
"not found in history" into "safe to resend", and no idempotency is claimed without documentation.

## B3. Cancelling a scheduled SMS

### B3.1 Endpoint and shape (documented)

`PUT /v3/sms/{message_id}/cancel`, operation `cancel-sms` (`sms.yaml` line 5926):

> "Use this endpoint to cancel a specific scheduled SMS. Unlike the **Cancel All SMS** endpoint,
> which cancels all scheduled SMS, this endpoint only cancels one specified scheduled SMS."

- Path parameter `message_id` (string, required): "The _message_id_ of the scheduled SMS to cancel."
- **No request body** is declared (the gem sends none; a contract spec pins both).
- Only a `200` response is declared, schema `cancel-sms`. Its example:
  `{"http_code":200,"response_code":"SUCCESS","response_msg":"Scheduled sms message has been cancelled.","data":null}`.
- `data` is `type: object` but described as: "This parameter is deprecated and will return
  **null**." The contract specs now list `sms_cancel` `/data` as a known example/schema
  inconsistency.
- **Archived (2022):** the example answered `"response_msg": "Message 307EF035-B7CE-4321-93CD-0753597B7293 has been cancelled."`
  with `"data": []`. So `response_msg` wording has changed and is not machine-readable.

### B3.2 Status codes and error cases (unknown)

No current or archived source documents what ClickSend answers to:
- a second cancel of the same message;
- a message that has already been sent (or whose schedule has passed);
- an unknown or malformed `message_id`;
- a message in `WaitApproval`, or a campaign message (help 42192 says campaign messages don't
  appear in SMS history and are cancelled as a whole campaign, so they may not be addressable
  here either: **unknown**).

The general status-code table (`index.html.md`) lists 400/403/404 generically; nothing ties them
to this operation. The only data point is indirect: `GET /v3/sms/receipts/{id}` answered 404
`NOT_FOUND` for a missing receipt live in 1.0. That says nothing about cancel.

### B3.3 Idempotency (unknown; decided: `idempotent: false`)

- No idempotency statement exists for this operation or any other (1.1 audit fact 1, re-checked:
  `grep -i idempot` over `sms.yaml` finds nothing).
- `index.html.md` "Verbs" only says `PUT` | "Update an item. Success returns `200` status code."
  That is REST vocabulary, not an idempotency promise.
- **Inferred:** in effect, cancelling twice can't cause a send, and the state transition
  (Scheduled → Cancelled) looks idempotent. But the *answer* to a repeat is unknown: if the
  first attempt succeeded and the response was lost, a retry could raise (e.g. 400/404), turning
  a success into a misleading failure.

**Decision: not idempotent.** The rule for this spike is that idempotency must come from
documentation. Consequences, all through the existing connection rules:
- 429, refused connections and connect timeouts are retried (not processed).
- Read timeouts, resets and 5xx are **not** retried and raise with `AmbiguousRequestError`.
- An error inside a 2xx body is ambiguous, as for every other call.

Is "not retried" the safe direction here? A missed cancel means a message the caller wanted
stopped may go out; that's recoverable by the caller (check, then cancel again). It never sends a
duplicate. The README tells callers a repeat cancel "can't send anything, but may raise even if
the first call worked".

### B3.4 Ambiguity: how a caller finds out (documented + inferred)

- `GET /v3/sms/history?q=message_id:<id>` is a documented filter, and `Cancelled` and
  `Scheduled` are documented history statuses (`q` description: "Available values for status
  are: Queued, Completed, Scheduled, WaitApproval, Failed, Cancelled, CancelledAfterReview,
  Received, Sent"). Help 42318 lists "Cancelled | 301 | Message is cancelled".
- **Inferred, not documented:** that a message cancelled through this endpoint shows `Cancelled`
  in history, and how soon.
- Receipts are no help: there's no documented receipt for a cancelled message, and test numbers
  never produce receipts.

The gem's README therefore says: when it matters (for example before scheduling a replacement),
check `client.sms.history(message_id:)` for `"Cancelled"`.

**Why this matters for duplicates.** Help 42192: "Scheduled Quick SMS messages cannot be
edited — if you need to change the message, recipients, or time, cancel it and create a new
scheduled message." *Reschedule = cancel + send.* If ClickSend answered 200 to a cancel of an
already-sent message (unknown), an app would send the replacement and the recipient would get
both. That is why:
- the docs never let "no exception" mean "won't go out" for undocumented cases;
- the FakeAPI refuses to answer undocumented cancels (B3.5) instead of guessing "success".

### B3.5 Prototype

```ruby
client.sms.cancel(message_id) # => nil; raises the typed error otherwise
```

- `lib/clicksend/resources/sms.rb`: `#cancel`. Validates the ID with the existing
  `message_id!` (it's interpolated into the path), `PUT` with no body, `operation: "sms.cancel"`,
  default (non-idempotent) retry rules, returns `nil` like the mark-read methods.
- Why `nil` and not a result object: `data` is deprecated and always null; `response_msg` is
  free text whose wording already changed between 2022 and now. A result object would wrap
  nothing machine-usable and add API surface to maintain.
- FakeAPI (`lib/clicksend/testing/fake_api.rb`): route `PUT /v3/sms/{id}/cancel`. It succeeds
  only for a message the fake accepted whose `schedule` is still in the future by the fake's clock,
  with ClickSend's documented answer, and it records it in `fake.cancelled_messages`. The message
  stays in `sent_messages` because ClickSend accepted it. For **every other case** (unknown ID,
  immediate message, past schedule, second cancel) it raises `Testing::StubError` naming the
  path to stub. A guess either way would be wrong. "Success" hides the reschedule duplicate.
  "404" invents an error contract that apps would come to rely on. `SentMessage` is unchanged,
  so `to_h`, equality and pattern matching stay compatible.
- `fail_next(..., processed: true/false, method: :put)` already works for ambiguous cancels.
- Specs: `spec/clicksend/resources/sms_cancel_spec.rb` (8 examples),
  `spec/clicksend/testing/cancel_and_history_spec.rb` (cancel part, 6 examples).
- Contract specs: the operation exists; no request body is documented and none is sent; `data`
  is still described as deprecated; the `sms_cancel.json` fixture matches the current example and
  the schema apart from `/data`.

### B3.6 `cancel-all` re-evaluated (documented)

`PUT /v3/sms/cancel-all`: "Use this endpoint to cancel all scheduled SMS." The request body is
optional, with one optional property:

> "`custom_string`: The scheduled messages to cancel with the specified _custom_string_. … This
> parameter allows you to cancel messages that have this _custom_string_. It's commonly used for
> canceling scheduled SMS campaigns."

The response is `data.count`, "The number of scehduled SMS cancelled" (example message "2 sms
messages have been cancelled.").

This is new relative to the 1.1 Rejected table, which described only the empty body. It doesn't
change the decision:
- Without the filter, or with an empty value (handling unknown), **every** scheduled SMS on the
  account is cancelled. The dashboard has the same bulk action (help 42192).
- How `custom_string` is matched is **unknown**: exact or partial, and case-sensitive or not.
  The general docs say searches "are **not** case-sensitive", and history calls a filter value a
  "text or keyword". With a partial match, `custom_string: "otp:4"` would cancel `otp:42`, `otp:43` and so on.
- Campaigns add their own `custom_string`, so a collision with an app's references is possible.

**Recommendation:** keep it unwrapped (README "not wrapped" list). Reconsider for 1.3 as
`sms.cancel_matching(custom_string:)` with a *required*, non-empty argument, and only after a live
check shows exact, case-sensitive matching. The new contract spec fails if ClickSend ever makes
the filter required, which is the signal to revisit.

### B3.7 Live verification protocol (for the owner to approve; free)

Uses only the documented free test number `+61411111111` ("No messages will be sent, and your
account won't be charged", `testing.md`) on an account with Australia enabled, with
`max_retries: 0`, from a console:

1. `m = client.sms.deliver(to: "+61411111111", body: "cancel probe", schedule: Time.now + 3600, custom_string: "probe:cancel:<uuid>")`
   and record `m.message_id`.
2. `client.sms.history(message_id: m.message_id)` at about 0s, 5s, 30s and 120s. Record whether
   and when the row appears, and its status (expected `Scheduled`). This also gives the first
   observed history-latency data point (B6).
3. `client.request(:put, "/v3/sms/#{m.message_id}/cancel")`. Record the HTTP status and the full envelope.
4. History again: is the status `Cancelled`, and how soon?
5. Cancel the same ID again. Record the answer: the repeat semantics.
6. Cancel a well-formed random UUID. Record the answer: the unknown-ID semantics.
7. Cancel the 2026-10-05 accepted test-number message (history status `Completed`). Record the
   answer: the already-sent semantics.
8. Balance before and after (`client.account.fetch.balance`).

Gate for 1.2: steps 3 to 7 recorded in `docs/clicksend-api-notes.md`. If step 7 answers SUCCESS,
the README must say so prominently ("a SUCCESS answer doesn't mean the message was stopped").
Abort conditions: any non-test number, or any balance change.

| Complexity | Low (8 lines of library code; ~45 lines in the fake) |
| Maintenance | Low; contract specs watch the path, the absence of a body, and the deprecated `data` |

## B4. Price quote (`POST /v3/sms/price`)

### B4.1 What is documented

- Description: "Use this endpoint to calculate the price of sending messages. The cost of
  sending messages varies based on the type and length of the message." (**documented**)
- Request: the same per-message fields as send (`body` required; `to`, `from`, `source`,
  `schedule`, `custom_string`, `list_id`, `contact_id`, `country`), plus top-level `senders`
  (smart assign) and `shorten_urls`. `show_summary` ("Used for showing additional information in
  the response") sits **inside the message item** in the schema, almost certainly misplaced
  (**documented defect**).
- Response `calculate-sms-price`: `total_price` (number), `total_count`, `queued_count`,
  `messages[]` (schema `sms`), `_currency`, `blocked_count`, and `_summary` (`test_message`,
  `countries` with `registration_type`, `usable_sender_id`, `selected`, and `regulation`, which
  holds `restricted_sending`, `trial_sending` and the registration IDs).
- Example inconsistencies: `_summary.countries` is an array in the schema and an object keyed by
  country in the example. The schema has `receipient_count` and the example `recipient_count`. The
  schema says `trial_sending` is a boolean and the example has `0`.

### B4.2 Side effects: the only statements

1. The `sms` schema's `date` property (`sms.yaml` ~line 383):
   > "Returned as a string since it may be an empty string in price-calculation responses where
   > no message has actually been sent yet."

   This is the **only** documentation statement on effects. It says (inside a field description)
   that a price calculation doesn't send the message. "Yet" is ambiguous wording but not a
   promise of a later send.
2. Response descriptions copied from send *contradict* that reading if taken literally:
   `total_count` "The total number of messages sent from the request"; `queued_count` "Messages
   scheduled to be sent right away will be sent immediately. If not, it will be queued."
   (**documented**, evidently copy-pasted.)
3. The current example returns `"message_id": "1EF50711-2787-68F4-8223-9F9C4393E380"` and
   `"status": "SUCCESS"`. The 2022 archived example had **no** `message_id` (**archived**).
   Whether an ID is reserved, recorded or visible in history is **unknown**.

Nothing (current, archived, help) says whether a quote:
- appears in history or statistics, or produces receipts;
- charges or reserves credit, or counts against trial-sending limits ("a daily limit of 200
  messages in some countries", `trial_sending` description);
- starts or extends the `THROTTLED` window ("Identical message body recently sent to the same
  recipient");
- counts against rate limits (undocumented everywhere; observed limits look per endpoint);
- is safe to repeat (no idempotency statement).

### B4.3 Decision

Not clearly documented as free of side effects, so **no public method was prototyped**. As the
brief requires, the existing path stays: `client.request(:post, "/v3/sms/price", body: …)`,
which treats `POST` as non-idempotent (a timeout raises `AmbiguousRequestError`, never a retry).
The README "not wrapped" list now says why.

An extra hazard for a wrapper: a quote result is shaped exactly like a send result (`messages[]`,
`status: "SUCCESS"`, `message_id`). A `Batch`-like return value would invite code to treat a
quote as a send, for example by storing its `message_id` or reconciling against it. A future
wrapper should return a distinct type with no `message_id` accessor and no `queued?`.

### B4.4 Evidence that would justify wrapping

Either:
- a ClickSend documentation statement (or written support answer) that `/sms/price` has no
  effects on billing, history, statistics, receipts, `THROTTLED` or limits; or
- the live protocol below, run on test numbers, showing no observable effect, **plus** acceptance
  that effects not observable from the API (internal counters) remain unknown and are documented
  as such.

### B4.5 Live verification protocol (needs owner approval; test numbers only)

With `max_retries: 0`, only `+61411111111` and `+61422222222`, and a unique
`custom_string: "probe:price:<uuid>"`:

1. Baseline: `account.fetch.balance`; `sms.history(to: "+61411111111", date_from: now - 600)`
   row count; rate-limit headers of one `POST /v3/sms/price` (`response.rate_limit`).
2. One price call for one message to `+61411111111`. Record `message_id`, `status`, `date`, HTTP
   status, all headers.
3. At about 10s, 60s and 300s: history `q=message_id:<id>` and `q=to:+61411111111` (search for the
   `custom_string`); `GET /v3/sms/receipts/<id>`; balance; `GET /v3/statistics/sms` outbound count.
   Expected if it has no effects: no row, a 404 receipt, the same balance, the same counts.
4. Repeat the price call: is the `message_id` new each time? Is the answer otherwise identical?
5. Optional, separate approval (it sends a free test-number message): within 5 seconds of a
   price call, `sms.deliver` the identical body to `+61422222222`. Not `THROTTLED`? Then the
   quote didn't start a throttle window for that number.
6. Rate limits: compare `x-ratelimit-remaining` on `/sms/price` and `/sms/send` before and after,
   to see whether they share an allowance.

Never use a real phone number: if the endpoint did send, it would deliver and charge.

## B6. Finding a message after an ambiguous send

### B6.1 Capabilities (documented)

`GET /v3/sms/history` (`view-sms-history`): "Use this endpoint to view previously sent SMS."
- `page`, `limit` (15..100).
- `q`: "Allows filtering of results based on your search criteria. The query should be in the
  format `field_name:value`." Fields: `Status`, `To`, `from`, `subaccount_id`, `message_id`.
  Value: "The text or keyword you're searching for within the specified field." **Exact or
  partial match: unknown.**
- `order_by`: `date` (default `date:asc`), `username`, `from`, `to`, `status`, `body`.
- `date_from`, `date_to`: integer Unix time, "Start date to filter results" / "End date to
  filter results". **Inclusive or not, and which timestamp (`date` or `schedule`): unknown.**
- Rows include `custom_string` (schema), but `custom_string` is **not** a `q` field.

General "Searching and Sorting" (`index.html.md`): "Most GET endpoints allow searching and
sorting. Searches are **not** case-sensitive." `q=field:value,field2:value`; "By default, it will
search using the `AND` operator", `operator=AND|OR`. **Correction to 1.1 wording:** the 1.1 README
said "ClickSend documents one search filter per request". More precisely, the *history operation*
documents a single `field_name:value` and no `operator`, while the general docs describe
combining fields. Whether history honours combinations is unverified, and the only extra field
that would help (`custom_string`) isn't searchable anyway. The README wording has been
corrected; `sms.history` keeps one filter.

Other related endpoints:
- `GET /v3/sms/history/export`: same filters plus `filename`; answers `data.url`, a pre-signed
  S3 URL (example host `clicksend-api-downloads.s3.ap-southeast-2.amazonaws.com`). Help 43125:
  dashboard downloads are capped at 50,000 records and the body is cut to 160 characters.
- `GET /v3/statistics/sms`: account totals and per-day `outbound`/`inbound`/`bounced` counts and
  prices; no parameters.
- `GET /v3/sms/receipts/{message_id}`: needs the `message_id`. After an ambiguous send, the
  caller never got one.
- `custom_string` echo: in receipts (unread list, POLL rule, after delivery) and replies.

### B6.2 Consistency and retention

- **No consistency guarantee anywhere.** Searched `sms.yaml`, `statistics.yaml`,
  `message-delivery.yaml`, `index.html.md`, the archived docs and help articles 42192, 42316,
  42317 and 43125 for "real-time", "immediately", "delay", "appear" and "eventual". The only hits
  are the send-queue sentences ("Messages scheduled to be sent right away will be sent
  immediately") and help 42317 on *delivery*, not history: "the message is forwarded to mobile
  networks almost instantly". (**unknown**)
- Help 43125: "ClickSend retains comprehensive message data for four months … After four
  months, your message data is archived, and no longer available to view in the Dashboard, or
  downloadable from the History page or API." (**help**)
- Help 43125: "If you have De-identify message history enabled, the to data will be partially
  obfuscated in any history downloads." Whether API history is affected: **unknown**. If it is,
  a `q=to:` search can't find anything.
- Help 42192: "Scheduled SMS Campaigns do not appear in SMS History". (**help**)
- Observed in 1.1 (2026-10-06): one test-number message from the day before was found with
  `q=to:`. That says nothing about latency.

So "absent from history" can mean: not yet visible, older than four months, de-identified, a
campaign, filtered out by window semantics, or never accepted. Only the last means "not sent".

### B6.3 Prototype: `sms.search_history`

```ruby
records = client.sms.search_history(to: "+61411111111", custom_string: "otp:42", sent_after: started_at)
# => Array<Clicksend::SMS::HistoryRecord>, possibly empty, possibly several
```

Semantics, in one sentence: *the outbound history rows ClickSend shows now for this recipient
whose `to` and `custom_string` exactly equal yours, sent within the (widened) window.* It makes
no claim about sending. Design decisions:

- **Name.** `search_history` ("search" implies results may be empty and settles nothing). It
  avoids `find_*` (Ruby's `find` returns one item, and "not found" reads as an answer),
  `sent?`/`delivered?` (a claim the data can't support), and anything with "not sent".
- **Return type: Array, not a three-valued object.** The tempting result object, `found` /
  `not_found_yet`, has only two real states, and the second is just "empty": ClickSend gives no
  signal to tell "not yet" from "never". A wrapper with a `not_found?` predicate makes the
  dangerous branch *easier* to write. An Array with the README's explicit "an empty result is
  not proof" is the least misusable option available. It also returns all matches, because a
  `custom_string` may legitimately repeat.
- **Required `sent_after:`.** It bounds the scan and forces the caller to think about the time
  of the attempt. `sent_before:` is optional (default: no upper bound), so a scheduled message,
  whose history `date` semantics are unknown, isn't cut off.
- **Window widened by `HISTORY_SEARCH_MARGIN` (300s) on each side.** Inclusivity and the clock
  behind `date` are unknown. Widening can only add rows, which are then matched exactly, so it
  errs toward "found" (a missed resend, recoverable) and never toward "not found".
- **Exact client-side match on `to`, `custom_string` and `direction == "out"`.** `q` values are
  "text or keyword" and searches are case-insensitive, so a server match isn't trusted. The test
  covers case variants, prefixes, a longer number containing the given one, and inbound rows.
- **`to` must be E.164** (`/\A\+[1-9]\d{5,14}\z/`). History stores E.164 (live and example), and
  a local-format number would silently match nothing, a false "empty".
- **Cost.** `limit: 100` (the maximum), every page read. With `q=to:` plus a window it is
  usually one request. Rate limits are undocumented (observed: 20/min on `GET /v3/account`, which
  seemed to be per endpoint), so the doc comment and README say each page is a request. No
  `max_pages` option: a cap would turn "didn't look" into "empty".
- **No polling or waiting built in.** Retrying the search later is the caller's policy. A built-in
  wait would imply that some duration is enough, which nothing documents.

Specs: `spec/clicksend/resources/sms_search_history_spec.rb` (7 examples).

### B6.4 Rejected alternatives

| Idea | Why not |
|---|---|
| `deliver(reconcile: true)` / "check then resend" | Already rejected in 1.1; nothing here changes it (no consistency guarantee) |
| A `not_found_yet` / `not_sent?` result | Encodes a state ClickSend can't report; invites `resend if result.not_found?` |
| History export | Answers an off-host pre-signed S3 URL. The gem refuses other hosts by design and has no CSV parsing (Faraday-only). The help centre says dashboard downloads cut bodies to 160 characters. No consistency advantage over `/sms/history` |
| Statistics | Aggregate per-day counts with no filters; can't identify a message, and concurrent sends make counts meaningless |
| Receipt by ID | The ambiguous send's `message_id` is unknown; receipts come only after delivery (never for test numbers); an absent receipt means nothing |
| Scanning the unread receipts list for `custom_string` | Needs a POLL rule; another consumer may already have marked them read; arrives only after delivery |
| Server-side `custom_string` filter via `q` | Not a documented field; a contract spec already fails if ClickSend documents it, which is the cue to use it |
| Multiple `q` fields (`to` AND `message_id`) | Documented generally, not for history; no extra value for this use |

### B6.5 FakeAPI

1.1 deliberately serves no history: an always-current history would let a "not in history, so
resend" rule pass its tests. That stays. The new helper only lets a test *state* what history
shows:

```ruby
fake.stub_history                                    # history shows nothing (yet)
fake.stub_history(fake.sent_messages.last)           # shows this message, status "Sent"
fake.stub_history(message, status: "Cancelled")
```

- Without `stub_history`, `GET /v3/sms/history` is still a 404 (the existing spec "does not
  serve history" still passes).
- Rows are built from `SentMessage`s in the live-observed shape (`status_code` and `status_text`
  null, `schedule` a String). The status must be a documented outbound history status.
- Every history request gets exactly those rows, whatever its `q`, date and order parameters, so
  the fake never decides undocumented filter semantics. Pagination is ClickSend's envelope.
- It is built on the existing `stub`, so a later `stub_history` or `stub` replaces it.

Specs: `spec/clicksend/testing/cancel_and_history_spec.rb` (history part, 5 examples).
