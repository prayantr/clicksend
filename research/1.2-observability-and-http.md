# 1.2 spike: OpenTelemetry adapter (B1) and persistent HTTP connections (B2)

Date: 2026-10-06. Branch `spike/1.2-observability-http`, from the 1.1.0 release commit `7e96b24`.
No ClickSend API was called. Every measurement used local servers.

**Summary**

- **B1 OpenTelemetry.** Ship it as a companion gem, `clicksend-opentelemetry`. A prototype
  is in `companions/clicksend-opentelemetry/`: 183 lines of code, 18 specs. It needed
  **no change to the core gem**. On the request thread it adds about 14 µs per call with the
  SDK, and about 3 µs when tracing is not configured.
- **B2 Persistent connections.** Support them as an **opt-in, documented adapter**, not as the
  default. They cut a simulated 25 ms RTT HTTPS send from 85 ms to 31 ms. On localhost TLS
  they give about 7x the requests/s. They add **no hidden retries**: this is pinned by real-socket
  specs.

  They do change three things for the worse, and the current README advice is unsafe because
  of the first:
  1. **A pool that is too small** makes sends fail as ambiguous `TimeoutError`s even though
     they never left the machine. With `pool_size: 2`, 8 threads and 25 ms RTT, 31 of 400
     sends failed this way. The README example uses `pool_size: 5`.
  2. **Keep-alive races** turn unprocessed sends into ambiguous errors. This happens when the
     server's idle timeout is shorter than the client's (5 s).
  3. **Errors before sending are reclassified.** A refused connection or a connect/TLS-handshake
     timeout can no longer be recognised as "not sent". Such a send is reported as ambiguous and
     is not retried.

  All three fail in the safe direction (no duplicate is ever sent), but they create
  reconciliation work.

## B1 OpenTelemetry

### The existing hook is sufficient

`instrument(name, payload) { }` with `request.clicksend` and `retry.clicksend` provides everything a span needs:

- **Before the block:** `http_method`, `path` (no query string), `operation` and `idempotent`.
  These give the span name and start attributes.
- **After the block:** `attempts`, `http_status`, `response_code` and `ambiguous`. These are the
  outcome attributes.
- **The exception:** the connection re-raises the call's error *inside* the block, so the
  instrumenter sees the exception class.
- **Retries:** `retry.clicksend` is published on the same thread inside the request block, so
  the adapter can find its span through the OpenTelemetry context and add an event.

Only one thing is missing: the **host**. `server.address` and `server.port` come from a
constructor option (`base_url:`, default `https://rest.clicksend.com`). I considered adding the
host as a payload key. That would mean passing `base_url` from `Client` into `Connection` and
coupling the companion to `clicksend >= 1.2`. Because base URLs other than the default are
essentially test servers, the option is the smaller change. **No core commit was needed.**

### Design (prototype: `companions/clicksend-opentelemetry/lib/clicksend/opentelemetry.rb`)

- **`Clicksend::OpenTelemetry::Instrumenter`**
  - **The span.** One CLIENT span per logical call, retries included. It is named
    `clicksend <operation>`, or `clicksend <METHOD>` when there is no operation. Paths are not
    used in the name because they can contain message IDs, which would make the name
    high-cardinality.
  - **Context.** The span is attached as the current context, so HTTP-level spans nest under it.
    The previous context is always restored.
  - **Retries.** Each `retry.clicksend` becomes a `clicksend.retry` event on the span.
  - **Robustness.** Every OpenTelemetry call is wrapped. A failure goes to
    `OpenTelemetry.handle_error`, and the request block is yielded exactly once whatever happens.
  - **Tracer lookup.** The tracer comes from the global provider when the instrumenter is built.
    Before `SDK.configure` that provider is the API's proxy, so it works in Rails initializers
    whatever order they run in.
- **`Clicksend::OpenTelemetry::FanOut.new(a, b, ...)`** combines instrumenters by nesting them.
  The request block still runs once. Put the OpenTelemetry instrumenter **last** (innermost).
  Then an ActiveSupport subscriber that raises after the request finished (the client already
  ignores such errors) is never recorded as the span's error. A spec covers this.

### Attributes and semantic conventions

| Attribute | Value | Note |
|---|---|---|
| `http.request.method` | `POST` | semconv (stable HTTP) |
| `server.address`, `server.port` | from `base_url:` | semconv |
| `url.path` | `/v3/sms/send` | Semconv requires `url.full` on HTTP *client* spans. This span is a logical operation spanning several attempts, not one HTTP request, so it does not claim to be an HTTP client span. It records the path (never the query: `sms.history(to:)` puts the phone number in the query). `record_path: false` turns it off. `url.template` would fit better but is still in development and the gem has no templates. |
| `http.response.status_code` | last response | semconv |
| `error.type` + status ERROR (description = class name) | `Clicksend::TimeoutError` | semconv. The status description is the class only. |
| `exception` event | `exception.type`, a safe `exception.message`, `exception.stacktrace` | `record_exception` is **not** used, because it records `exception.message` and `full_message`. API errors carry ClickSend's `response_msg`, and foreign exceptions can carry anything. The safe message is class + HTTP status + `response_code` + request line, all of which are already in the payload. |
| `clicksend.operation`, `.idempotent`, `.attempts`, `.ambiguous`, `.response_code` | from the payload | Custom namespace. `http.request.resend_count` was not used: semconv defines it per physical request. |
| event `clicksend.retry` | `clicksend.retry.attempt`, `clicksend.retry.delay` (s), `error.type`, `http.response.status_code` | |

The exported spans never contain phone numbers, message text, `custom_string`, credentials,
`Basic`, `q=` or `to:`. A spec checks this, including a 429 retry, a history search and a 400.

### Nesting with HTTP-level instrumentation (`bench/otel_nesting.rb`)

The scenario is one `sms.history(to:)` call that fails with a 503 and succeeds on retry, using
the default adapter. Output:

```
clicksend only:
- clicksend sms.history [client] {status 200, url.path, attempts 2} events=[clicksend.retry]
+ faraday:
- clicksend sms.history [client] ...
  - GET [client, Faraday] {503, url.full=http://127.0.0.1:…/v3/sms/history?q=to%3A%2B61411111111}
  - GET [client, Faraday] {200, url.full=…?q=to%3A%2B61411111111}
+ net_http:
- clicksend sms.history [client] ...
  - connect [internal, Net::HTTP]
  - GET [client, Net::HTTP] {503, url.path, url.query=q=to%3A%2B61411111111}
  - connect [internal, Net::HTTP]
  - GET [client, Net::HTTP] {200, ...}
+ faraday + net_http:  identical to "+ faraday". The Faraday middleware runs the adapter
  untraced (enable_internal_instrumentation: false), so the Net::HTTP spans are suppressed.
```

- **Nesting.** The clicksend span is the parent of one HTTP span per attempt. This is the shape
  semconv recommends: a logical operation with resend attempts as children.
- **Query strings in HTTP spans (a README warning, not a bug in this gem).** The Faraday and
  Net::HTTP instrumentations record the query string, so a history search by number puts the
  number in `url.full` or `url.query`. They also send a `traceparent` header to ClickSend.
  Applications that need to avoid this should configure those instrumentations, or not
  install them.
- **Persistent connections.** With net_http_persistent, `connect` spans appear only for new
  connections.
- **No double reporting.** The adapter does not subscribe to ActiveSupport, so existing
  `ActiveSupport::Notifications` subscribers see exactly the same events and payloads as before.
  A spec compares the payloads with and without `FanOut`. If an app *also* bridges
  `request.clicksend` to spans itself, it should pick one approach.

### Safety evidence (companion specs)

These run on FakeAPI, and over real sockets with Faraday and Net::HTTP instrumentation installed.

- **Send timeout.**
  - FakeAPI `fail_next(:timeout, processed: true)`: `TimeoutError`, ambiguous, `attempts == 1`,
    1 request. The span has `clicksend.ambiguous=true` and no status code.
  - Real socket, server hangs: the server received `POST /v3/sms/send` exactly once.
- **The tracer fails.** A tracer whose `start_span` raises, and a span whose `add_attributes` and
  `add_event` raise:
  - the request still runs exactly once and returns its result;
  - a timeout stays ambiguous and single-attempt;
  - the error is reported through `OpenTelemetry.handle_error`;
  - the context is clean afterwards.
- **A 500 on a send** gives span status ERROR, `attempts == 1`, ambiguous, and an exception
  message without the response text.
- **Retries:** two 503s on a GET give 3 attempts, 2 `clicksend.retry` events and 3 child HTTP spans.

The benchmark runs 20,000 `sms.deliver` calls over an in-memory transport that returns the
fixture response (no Faraday, no network). Each configuration was run 3 times; the table shows

### Companion gem vs opt-in file in core (soft dependency)

| | Companion `clicksend-opentelemetry` | `require "clicksend/opentelemetry"` in core (undeclared dependency) |
|---|---|---|
| Dependency declaration | `opentelemetry-api ~> 1.1` and `clicksend >= 1.1, < 2` are declared, so Bundler enforces them | Not expressible. A future OTel API 2.0 would break at runtime with no resolver protection. The core needs `defined?` checks and a friendly `LoadError`. |
| Core constraints | None. Faraday stays the only runtime dependency, and core CI, the audit and Standard are unchanged. | The root Gemfile needs `opentelemetry-api`/`-sdk` as dev dependencies, which enlarges core CI's install and `bundle-audit` surface. Every core release ships OTel code. |
| Release process | A second gem: gemspec, CHANGELOG, MFA push, ownership. Can release without a core release. | One gem, but OTel fixes force a core release. |
| Version coupling | Only the public instrumenter contract, which 1.x semver protects. Kept in this monorepo with `path:` so its specs always run against the current core. | Tight. Semconv churn (attribute renames) lands in core minors. |
| Discoverability | Needs a README pointer | Built in |
| Maintenance | A CI job (working-directory) and a matrix against released core versions | Smaller footprint but mixed concerns |

**Decision: companion gem.** This revises the 1.1 roadmap's "soft dependency, no gemspec change".
The deciding factors are the ones a soft dependency cannot provide: a declared OTel API range,
and keeping OpenTelemetry out of the core's dependency, CI and audit surface. The coupling is
limited to an already-public, semver-protected hook.

## B2 Persistent connections

### Today

`faraday-net_http` 3.4.4 creates a `Net::HTTP` object for every request (`net_http_connection`)
and runs the request inside `http.start do … end`. That opens and closes a TCP connection, plus
a TLS handshake, every time. The benchmarks confirm it: `connections_opened == requests` for
every default-adapter row. It sets `http.max_retries = 0`, which the 1.1 suite already pins.

### Methodology

**Server (`bench/support/keep_alive_server.rb`).** A thread-per-connection HTTP/1.1 keep-alive
server on 127.0.0.1. It serves plain HTTP or TLS with a throwaway CA. The client trusts that CA
through `SSL_CERT_FILE`, so **no verification setting was changed**. Responses are the real
fixtures `sms_send.json` (1.1 KB) and `account.json`. The server counts accepted connections and
fully received requests. It can misbehave on any request (close, reset, hang), close idle
connections, and emulate the keep-alive race (`close_delay`).

**Throughput benchmark (`bench/http_bench.rb`).**
- The server runs in a **forked child process**, so its threads and allocations do not count
  against the client. Stats are fetched over a pipe.
- The client calls `client.sms.deliver` (the full path: JSON, Faraday, HTTP, parsing, result
  objects) with `max_retries: 0`.
- Measured:
  - req/s, p50 and p95 per request (monotonic clock);
  - allocations per request (`GC.stat(:total_allocated_objects)`, single-thread rows only);
  - connections opened (server accepts, excluding one warm-up request);
  - client sockets still open (`lsof`).

**Simulated latency.** The server delays every response by 1 RTT, and every new connection by
1 RTT (TCP) or 2 RTT (TCP + TLS 1.3 handshake) before the handshake or first read. This
**models** latency on one side; it is not network emulation (`dnctl`/`tc` need root).
Limitations:
- the TLS 1.2 handshake (3 RTT) and TCP slow start are not modelled;
- the CPU cost of the handshake is real but localhost-sized;
- ClickSend's real RTT depends on where the caller is and was not measured here.

Treat the 25 ms rows as "1 RTT saved per request (plain) or 2 RTT saved per request (TLS)", not
as a prediction.

**Noise.** The table shows run 1; run 2 is in the appendix. Localhost multi-threaded rows vary by
±30% between runs (8 client threads on 8 cores, plus the server process). The RTT-dominated rows
vary by less than 3%.

What the numbers show:
- **Latency.** Over TLS with 25 ms RTT, p50 drops from 84 ms to 31 ms: the two handshake round
  trips disappear. Plain HTTP saves one RTT.
- **CPU.** On localhost TLS, req/s rises 7x. The handshake is the dominant client-side CPU cost.
- **Allocations.** Roughly the same: +49 per request on plain HTTP, −22 on TLS.
- **Connections.** One per thread instead of one per request. Separate clients do not share a
  pool: 4 clients means 4 connections.
- **Pool too small.** With pool size 2 and 8 threads, throughput is limited by the pool, and
  threads that wait more than 0.5 s get ambiguous errors (see S4 below).
- **`Client#with` per call** builds a new pool every time. Nothing is reused, and the sockets
  stay open until garbage collection.

### Semantic findings (`bench/spec/persistent_connection_spec.rb`, 36 real-socket specs, plain and TLS; 5 consecutive green runs)

**S1. No hidden retries of non-idempotent requests.**

On a *reused* connection, the server receives the request and then either closes without
replying or resets:
- `POST /v3/sms/send` arrives **exactly once**. The error is `ConnectionError`, ambiguous,
  `request_may_have_been_sent? == true`, `attempts == 1`.
- A non-idempotent `PUT /v3/sms/receipts-read` also arrives exactly once.
- An idempotent GET is retried only by the gem's own visible retry (`attempts == 2`).

Why, from the source:
- **net-http-persistent 4.x** has no retry logic of its own. `retry_change_requests` was removed
  in 4.0.0, and `request` does `rescue Exception → finish connection; raise`.
- **Net::HTTP** retries `GET HEAD PUT DELETE OPTIONS TRACE` (never POST) up to `max_retries`, on
  `ReadTimeout`, `EOFError`, `ECONNRESET`, `EPIPE`, `SSLError` and similar errors.
- **net-http-persistent defaults `max_retries` to 1.** The **control spec** shows the hazard:
  raw `Net::HTTP::Persistent` (no Faraday) sends that PUT **twice**, silently, while it sends a
  POST once.
- **faraday-net_http_persistent sets `http.max_retries = 0` on every request**, and
  net-http-persistent copies it onto each pooled `Net::HTTP` at checkout. I checked every
  Faraday-2-compatible release: 2.1.0-2.3.1 set it directly; 2.0.0-2.0.2 subclass `NetHttp` and
  inherit `configure_request`, which sets it.
- This is the load-bearing line. Any future documentation of the adapter must ship the control
  and PUT specs, so a regression in that gem fails CI.

**S2. Timeouts are preserved.**
- A read timeout (0.3 s) on a reused connection raises after under 0.7 s. The send is
  ambiguous and arrived once.
- The timed-out connection is **discarded**. The late response is never read as the next
  request's response: the next call gets a fresh connection and its own body.
- Open timeout applies to new connections, including the TLS handshake.
- `idle_timeout` (5 s) and `keep_alive_timeout` (5 s) are enforced before a request is written,
  which is safe.

**S3. Stale connections are replaced before the request is written.**
- Net::HTTP's `begin_transport` reconnects *before writing* if the socket is closed, older than
  `keep_alive_timeout`, or readable-at-EOF.
- A connection the server closed while idle (0.2 s) is therefore replaced transparently: the
  send succeeds on a new connection and arrives once. This holds for TLS too (close_notify).
- A server that answers `Connection: close` costs only a reconnect.

**S4. Pre-send failures are misclassified as "may have been sent" (safe, but a regression).**

| Failure before anything is written | default adapter | net_http_persistent | why |
|---|---|---|---|
| Connection refused | not sent: retried, not ambiguous | **possibly sent: ambiguous, not retried** | `Net::HTTP::Persistent::Error "connection refused: …"`, which `NOT_SENT_ERRORS` does not recognise |
| Connect/TLS-handshake timeout | not sent | **possibly sent** | `Net::OpenTimeout` escapes as `Timeout::Error` and becomes `Faraday::TimeoutError`, which the transport maps to `TimeoutError` with `request_sent: nil` |
| **Pool exhausted** (all `pool_size` connections in use for more than 0.5 s) | n/a | **`TimeoutError`, ambiguous**, and the server received nothing | `ConnectionPool::TimeoutError < Timeout::Error`, raised by the `TimedStack#pop` default `timeout: 0.5`; this wait cannot be configured through Faraday |

The pool-exhaustion case is the serious one. The README currently says
`adapter: [:net_http_persistent, {pool_size: 5}]`, and Sidekiq's default concurrency is 5 but is
commonly 10-25. Once more threads than `pool_size` send at once and responses take more than
about 0.5 s, sends start failing as ambiguous. The benchmark shows 31 of 400 (8%) at only 25 ms
RTT with 8 threads and pool 2. Each one forces a reconciliation, although nothing was sent.

**Mitigations:**
1. Document `pool_size >=` the number of threads that share the client: Puma threads, Sidekiq
   concurrency, or `RAILS_MAX_THREADS`. Never use a smaller fixed number.
2. *(Core change, recommended for 1.2 if the adapter is documented.)* In
   `Transport::Faraday#call`, inspect `Faraday::TimeoutError#wrapped_exception` and
   `ConnectionFailed`'s cause, and treat these as `request_sent: false`:
   - `Net::OpenTimeout`;
   - `ConnectionPool::TimeoutError`, matched by class name so there is no dependency;
   - `Net::HTTP::Persistent::Error` whose message starts with `connection refused:` or `host down:`.

   All of these are raised in `connection_for`, before `http.request`. Matching on the message
   is brittle, but it fails safe: if the message changes, the error falls back to "may have
   been sent". This needs its own commit and real-socket specs; it was not done in this spike.

**S5. Keep-alive race (`bench/cleanup_and_race.rb`).**

- **The case S3 cannot catch.** S3 handles a FIN that has already arrived. If the server closes
  an idle connection while the client is writing (the FIN is still in flight), the request is
  discarded unread and the client gets `ECONNRESET` or `EOF`. That is correctly ambiguous for a
  POST, but the request was never processed.
- **Emulation.** The server's idle timeout is 0.2 s, and requests arriving in the following
  20 ms are discarded with an RST.
- **Results (150 sends each).**

  | Client | Gaps between requests | Outcome |
  |---|---|---|
  | default adapter | 0.15-0.25 s | 150/150 sent |
  | persistent | 0.15-0.25 s | **27 of 150 (18%) ambiguous `ConnectionError`s**; the server discarded 26 unread, received 123, and received no duplicates |
  | persistent | 0-0.15 s (always below the server timeout) | 150/150 sent |

- **When it matters.** A request is exposed if it reuses a connection idle for between the
  server's keep-alive timeout T_s and T_s plus the one-way delay. Because net-http-persistent
  discards connections idle for 5 s or more, **the race only exists if the server (or its load
  balancer) times out idle connections in under 5 s**. With the common 60-75 s defaults (ALB,
  nginx) it does not occur.
- **Open item.** ClickSend's keep-alive timeout is unknown. Measuring it needs one live
  connection observation, and the owner must approve that; this spike made no API calls. If it
  is under 5 s, set `idle_timeout` below it, which needs a transport option (see API surface).

**S6. Thread safety.** The pool is shared, but each thread checks out its own connection, keyed
per thread and host. With 8 threads × 20 requests on one client and `pool_size: 8`, every
response matched its own request (each echoed its path) and at most 8 connections were opened.
The adapter mutates the shared `Net::HTTP::Persistent` settings on each request
(`read_timeout=`, `max_retries=`). That is racy, but every thread writes the same values.

**S7. Fork safety.**
- **What happens.** connection_pool 2.4 and later prepends a `Process._fork` hook that, in the
  child, checks in and closes every pooled connection (`auto_reload_after_fork`, default true;
  this gem's pool inherits from `ConnectionPool`).
- **Tested.** A forked child opened its own connection, and the parent kept working. This was
  tested for plain HTTP and TLS. With TLS, the child's close sends close_notify on the shared
  socket, so the server drops the parent's connection; the parent's next request detects EOF
  and reconnects before writing.
- **Risk.** net-http-persistent allows `connection_pool >= 2.2.4`. With 2.2-2.3 (no fork hook),
  a Puma or Sidekiq-swarm worker could share the master's socket, and responses could be read by
  the wrong process. **Require connection_pool >= 2.4 in documentation**, and ideally check it
  at runtime in a helper.

**S8. TLS is unchanged** for both adapters:
- a CA-trusted certificate for the host is accepted;
- a self-signed certificate is rejected, and the server receives 0 requests;
- a trusted certificate for another host name is rejected, and the server receives 0 requests.

The adapter sets `VERIFY_PEER` and the system cert store (Faraday's `ssl.verify` defaults to
true). Hostname verification is Net::HTTP's default. Pooled connections are verified at their
handshake and are never downgraded.

**S9. Cleanup.**
- A connection the server closed while idle sits in `CLOSE_WAIT` in the client until it is next
  used (then replaced) or garbage-collected. It is never read from: the EOF check runs first.
- Dropped clients' sockets stay `ESTABLISHED` until garbage collection. 20 discarded clients
  left 15 open sockets, all closed by `GC.start` through the IO finalizers. The default adapter
  holds no socket between calls.
- **There is no `Client#close`**, so a long-lived process that rebuilds clients leaks sockets
  until GC. The fix is to use one client per credential set, as the README already advises, and
  never call `with` per request.

### Other options

**httpx (`httpx/adapters/faraday`).** Rejected, on source reading only (not benchmarked).
- Its Faraday adapter uses `HTTPX.plugin(:persistent)`, which **always loads the `retries`
  plugin with `max_retries >= 1`**.
- That plugin retries `GET OPTIONS HEAD PUT DELETE` on reconnectable errors. That is the same
  PUT hazard as S1, without a Faraday-level `max_retries = 0` to disable it.
- Its exception classes would also need new not-sent mappings.
- HTTP/2 multiplexing would help only at volumes ClickSend's rate limits (about 20 requests per
  60 s observed on `/v3/account`) make unlikely.

**`faraday-net_http` with a reused `Net::HTTP`.** Not possible: the adapter always uses `start`
with a block.

### B2 recommendation

| | |
|---|---|
| User value | Real but narrow. It saves 1-3 RTT plus a TLS handshake per call. That matters for latency-sensitive synchronous sends and for batch jobs that make many calls. ClickSend's rate limits cap throughput gains for most users. |
| Complexity | Low for documentation only. Medium if the S4 classification fix and the specs are added to core. |
| Maintenance | The guarantee depends on a third-party line (`max_retries = 0`) and on connection_pool's fork hook. Both must be pinned by specs in CI. |
| API surface | Today: `adapter: [:net_http_persistent, {pool_size: N}]`, unchanged. No helper, because a helper would need a soft dependency and still could not size the pool for the app. If the ClickSend server timeout turns out to be under 5 s, the transport would need a way to set `idle_timeout` (Faraday allows it only through an adapter block). |
| Dependency impact | As a default: +3 runtime gems (faraday-net_http_persistent, net-http-persistent, connection_pool), which breaks the "Faraday is the only runtime dependency" rule. As opt-in: none. |
| Security | TLS verification unchanged (S8). Idle sockets live longer. Fork sharing is a risk with connection_pool < 2.4 (S7). |
| Compatibility | faraday-net_http_persistent >= 2.1, which needs Faraday >= 2.5. 2.0.x inherits `max_retries = 0` but was only source-read, not tested. connection_pool >= 2.4 for fork safety. Ruby >= 3.3. |
| Evidence | 36 real-socket specs; 2 benchmark runs; race and cleanup probes; source reading of net-http 0.9.1, net-http-persistent 4.0.8, faraday-net_http_persistent 2.0.0-2.3.1, connection_pool 3.0.2 and httpx 1.8.4 |
| **Recommendation** | **Opt-in, documented adapter. Not the default; no gem-provided helper.** For 1.2: (1) **fix the README now**: size `pool_size` to the threads sharing the client, require `faraday-net_http_persistent >= 2.1` and `connection_pool >= 2.4`, say that `with` builds a new pool, and say that refused connections, connect timeouts and pool waits are reported as ambiguous; (2) move `bench/spec/persistent_connection_spec.rb` (S1-S4 at least) into the core suite, with `faraday-net_http_persistent` as a *development* dependency in the root Gemfile, so CI pins the no-hidden-retry guarantee the README relies on; (3) implement the S4 not-sent classification in `Transport::Faraday` as its own commit; (4) measure ClickSend's keep-alive timeout once, with owner approval, before recommending the adapter for latency-sensitive sends. |

The benchmarks alone would argue for adopting persistent connections. The semantics argue
against making them the default: every new failure mode is safe (no duplicates were possible in
any test), but each one turns a send that never left into an ambiguous outcome, and that costs
the user reconciliation work. That trade-off belongs to the user, and the user can make it only
with documentation that states it.
