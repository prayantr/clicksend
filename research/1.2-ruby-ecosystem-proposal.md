# clicksend 1.2: Ruby ecosystem proposal

Status: research proposal, written 2026-10-06 on branch `research/ecosystem` (from the 1.1.0
release commit `7e96b24`). 1.1.0 is frozen; nothing here changes it. No integration was built:
the code below is either an illustrative sketch or a throwaway experiment.

The invariant every recommendation keeps:

> An ambiguous SMS must never become an automatic duplicate merely because a framework retries a job.

## 0. Executive recommendation

1. **No companion gem in 1.2.** In 1.2, change the core's documentation and test support. Most of
   what a `clicksend-rails` gem would contain is 3 to 30 lines of application code, and the
   experiments show that the dangerous parts are about *configuration of the job runner*, which a
   gem can't change for you.
2. **The README job recipe is right but incomplete.** It stops framework *retries* from repeating
   an ambiguous send (verified). It does **not** stop a *re-run after the worker dies or is shut down
   mid-send*. With a real Sidekiq 8.1.7 process, SIGTERM during a send made the README job send
   twice (experiment 2). Two mitigations were verified:
   - a client read timeout shorter than the worker's shutdown timeout turns that duplicate into an
     ordinary ambiguous error;
   - an in-flight marker committed on the application's own row prevents the second send even
     after a SIGKILL or a double enqueue (experiment 3).

   1.2 should document both.
3. **Core 1.2 additions (small, dependency-free):**
   - `require "clicksend/testing/rspec"` and `require "clicksend/testing/minitest"`: a
     `have_sent_sms` matcher and `assert_sms_sent`/`assert_no_sms_sent` over `FakeAPI`;
   - a FakeAPI failure mode that simulates the worker dying after ClickSend processed the send
     (`fail_next(:interrupted, processed: true)`), so applications can test their in-flight
     marker;
   - documentation recipes: a timeout budget for jobs, retry-declaration pitfalls, an in-flight
     marker, Sidekiq, Noticed, structured logs, metrics, Rails 8.1 `Rails.event`, and a warning
     about OpenTelemetry HTTP auto-instrumentation.
4. **`clicksend-rails`: yes, but in 1.3 and only if there is demand.** It would be a Railtie for
   `config.clicksend` and credentials, Rails.logger and ActiveSupport::Notifications on by default,
   an ActiveJob concern that intercepts ambiguity in `around_perform` (unaffected by the order of
   `retry_on` declarations, verified), a boot-time timeout-budget warning, test-environment wiring
   and a `Rails.event` bridge.
   - Not in it: an engine, routes, migrations, a gem-owned ledger table, an ActionMailer-like
     "texter" layer.
5. **`clicksend-opentelemetry`: 1.3, as a separate gem, not a core file.** The generic Faraday
   instrumentation already traces this gem's requests and records the **full URL with the query
   string**. For `sms.history(to:)` that is the recipient's phone number (verified). A dedicated
   instrumenter is worth having, but OpenTelemetry's semantic conventions are still changing, so
   it should be released on its own schedule.
6. **Never:**
   - `clicksend-sidekiq` (Sidekiq's own `sidekiq_retry_in` already returns `:kill`/`:discard`,
     verified);
   - a separate `clicksend-rspec` gem;
   - a global `Clicksend.configure`;
   - an ActionMailer-style delivery abstraction;
   - a gem-owned send ledger table;
   - monkey-patching Faraday or job frameworks.

## 2. Findings that drive the decisions

**F1. Framework retries are solved by the 1.1 recipe, but only if the order is right.** Rails
matches `rescue_from` handlers bottom-up, including those from `retry_on`/`discard_on`.
`discard_on Clicksend::AmbiguousRequestError` placed *above* `retry_on Clicksend::Error` is
silently overridden, which led to a duplicate in experiment 1D. An app-wide
`retry_on StandardError` in `ApplicationJob` is common. It is safe only because subclass handlers
are checked first (1E), and only while the subclass declares one.

**F2. Retry layers stack.** ActiveJob's `retry_on` re-raises when exhausted; on Sidekiq the wrapper
job then gets Sidekiq's own 25 retries (experiment 2). Noticed delivery methods are ActiveJob jobs
whose SMS methods re-raise on non-2xx and on network errors. `Noticed::ApplicationJob` declares no
retries, so the *backend* retries them. Any ambiguous error that escapes `perform` is retried by
some layer.

**F3. Shutdown re-runs are a different failure from retries, and the recipe can't see them.**
- Sidekiq's `hard_shutdown` pushes in-progress jobs back to Redis and then raises
  `Sidekiq::Shutdown` in the worker threads.
- The gem lets that `Interrupt` through, as it should: it isn't a `StandardError`, and
  `Connection#instrumented` re-raises anything that arrives while a request is `:running`.
- The re-run sends again (experiment 2).
- Defaults:

  | Runner | Default grace period |
  |---|---|
  | Sidekiq | `timeout: 25` |
  | Solid Queue | `shutdown_timeout` 5s (from its README; not run here) |
  | Heroku, Kubernetes | 30s |

  All are at or below the gem's default 30s read timeout.
- The dangerous window is exactly one attempt's read timeout. Connect timeouts and backoff sleeps
  are safe to interrupt, because nothing was sent.

**F4. Only persistence can close the remaining gap, and it must be the application's.**
- A compare-and-set "claim" on the domain row, committed before the HTTP call, survives SIGKILL,
  requeues and double enqueues (experiment 3).
- Doing the claim inside a transaction around the call does not work: the transaction is rolled
  back.
- The marker belongs on the row that already represents "this notification", for example
  `notifications.sms_state`. That row is in the app's database and schema. Its state means
  something to the domain ("unknown, needs reconciliation"), and it can be updated alongside other
  domain state.
- A gem-owned ledger table would duplicate that state and add migrations and multi-database
  concerns, plus retention and personal-data questions.

**F5. Generic APM auto-instrumentation undoes the gem's privacy work.** The gem keeps query strings
out of logs, errors and events. OpenTelemetry's Faraday instrumentation records `url.full` with the
query anyway, and `q=to:+61…` is a phone number. The span name is just `"GET"`. Other vendors'
HTTP integrations should be assumed to behave the same until checked.

**F6. Rails 8.1 changed what "Rails-native observability" means.**
- `Rails.event` (ActiveSupport::EventReporter) is fed by `StructuredEventSubscriber`s that consume
  ActiveSupport::Notifications.
- 1.1's `request.clicksend`/`retry.clicksend` events slot straight in with
  `attach_to :clicksend` (experiment 4).
- No change to the core is needed.

**F7. Ruby developers' expectations are split, and the trend favours instances.**
- twilio-ruby and octokit offer a global `configure`.
- aws-sdk-ruby has `Aws.config` defaults merged into clients.
- stripe-ruby, the reference API client, is moving users from globals to `StripeClient` instances
  and says new endpoints will only be reachable there.
- The Rails-specific expectations are well established, and aws-sdk-rails is the clearest model:
  - credentials under a top-level key;
  - Rails.logger;
  - ActiveSupport::Notifications on by default;
  - framework integrations shipped as separate gems.

**F8. Testing support is already 90% there.** `FakeAPI#sent_messages` returns `Data` objects that
work with every RSpec composable matcher. What is missing:
- concise failure messages;
- a Minitest assertion;
- a way to simulate the at-least-once re-run (F3/F4), the one duplicate path users can't test
  today.

## 3. Answers to the ten questions

### Q1. Should `clicksend-rails` exist?

**Yes, eventually. Not in 1.2.**
- Its one piece of real value is an ActiveJob concern that enforces ambiguity handling regardless
  of `retry_on`/`discard_on` order or inherited policies (F1), plus a boot-time check of the
  timeout budget (F3).
- Everything else (credentials, logger, notifications, test wiring) is boilerplate an initializer
  already handles.
- Ship the concern first as a ~25-line README snippet in 1.2. Promote it to a gem in 1.3 if:
  - users ask for it (issues, or downloads of a pre-release);
  - someone commits to a Rails 7.2/8.0/8.1 CI matrix.
- Precedents: aws-sdk-rails and postmark-rails show that the Rails layer is normally a separate
  gem.

### Q2. What should it contain? (1.3, if built)

1. A Railtie that reads `config.clicksend` (options) and `credentials.clicksend`
   (`username`, `api_key`) and builds **one frozen application client**, exposed as
   `Clicksend::Rails.client`. It is not a global configuration: it is built once at boot and never
   mutated. The logger defaults to `Rails.logger` and the instrumenter to
   `ActiveSupport::Notifications`.
2. `Clicksend::Rails::SendsSms`, an ActiveJob concern. It:
   - wraps `perform` in `around_perform` and rescues `Clicksend::AmbiguousRequestError`;
   - calls `on_ambiguous_sms(error)` (default: log and report through `Rails.error.report`);
   - swallows any failure of that hook after logging it;
   - never re-raises an ambiguous error.

   Verified to beat declaration order (experiment 1F).
3. A boot-time timeout-budget check that warns when the client's read timeout is at least the
   detected job runner's shutdown grace period:
   - Sidekiq: `Sidekiq.default_configuration[:timeout]`;
   - Solid Queue: `SolidQueue.shutdown_timeout`.

   It warns; it never fails boot.
4. Test-environment wiring. With `config.clicksend.test_mode = :fake` (default in `test`), the
   app client uses a `FakeAPI` exposed as `Clicksend::Rails.fake`, reset by included RSpec and
   Minitest hooks.
5. A `Rails.event` bridge (Rails ≥ 8.1): a `StructuredEventSubscriber` emitting
   `clicksend.request` and `clicksend.retry`.
6. Optional, after the marker recipe has been used in practice: a helper over an
   **app-provided** column, `claim_sms!(record, column: :sms_state)`, with no migration and no
   table of its own.

### Q3. What should it NOT contain?

- A Rails engine, routes or a webhook controller. ClickSend pushes are unauthenticated, and a
  mounted endpoint with a default path pattern would invite deployments without the secret
  segment. Keep the README controller.
- Migrations or a gem-owned `clicksend_deliveries` ledger (F4).
- An ActionMailer-like `Texter`/`deliver_later` layer (Q7).
- Autoloading a global client into `ActiveJob::Base`, or monkey-patching ActiveJob, Sidekiq or
  Faraday.
- A Noticed delivery method as a dependency (a recipe is enough; Q7).
- Any reconcile-then-resend automation (rejected in 1.1: history consistency is undocumented).

### Q4. ActiveJob support: in the companion, and can it enforce the invariant better?

The companion, with a README snippet first. It can enforce more than the recipe can, at three
levels:

| Level | Recipe (1.1) | Concern (proposed) | Marker (app persistence) |
|---|---|---|---|
| Framework retry of an ambiguous error | Yes, if the rescue is written correctly | **Yes, whatever `retry_on`/`discard_on` order or inheritance** (1F) | Yes |
| Exception *after* an accepted send (e.g. a DB update fails) | No: retried, sends again | No (it can't know a send happened) | **Yes**: the row stays `sending`, so the re-run reconciles |
| Worker shutdown mid-send | No (2) | Partly: a boot warning about the timeout budget | **Yes** (3) |
| Worker SIGKILL or OOM, reliable fetch, double enqueue | No | No | **Yes** (3) |

**Whose table?** The application's, on the domain row (`notifications.sms_state` or similar),
claimed with a conditional `UPDATE ... WHERE sms_state = 'pending'` committed before `deliver`.
On an ambiguous error, set `unknown` and reconcile. On a not-processed error (`retryable?`),
release the claim back to `pending` and re-raise. The gem cannot own this. It can only document it,
make it testable (FakeAPI `:interrupted`), and later offer a column helper.

### Q5. A dedicated Sidekiq integration?

**No gem. Recipes in 1.2.** Sidekiq already provides every primitive (experiment 2):
- `sidekiq_retry_in { |_, e| :kill if e.is_a?(Clicksend::AmbiguousRequestError) }` sends the job
  to the Dead set, calls `sidekiq_retries_exhausted`, and fires `death_handlers`. **Warning:**
  the Web UI's "Retry Now" on a dead job resends. Prefer the README recipe (rescue and reconcile)
  and keep `:kill` as a safety net.
- `:discard` drops the job silently, which loses the evidence. Don't recommend it.
- The shutdown requeue (F3) is not configurable away. The fix is to set the client's read timeout
  plus a margin below `-t`/`:timeout`. A job-specific client works:
  `JOB_CLICKSEND = CLICKSEND.with(timeout: 15, retry_policy: RetryPolicy.new(max_retries: 1, max_retry_after: 5))`.
  Sidekiq Pro/Enterprise reliable fetch also recovers SIGKILLed jobs, which re-run, so the marker
  is the only full answer there.
- ActiveJob on Sidekiq: `retry_on` exhaustion falls through to Sidekiq's 25 retries. That is safe
  only because ambiguous errors never escape `perform`. Say so in the docs.
- A global Sidekiq server middleware that swallows ambiguity for every job is possible (~15 lines),
  but it hides errors process-wide. Document it as an option, not a default.

### Q6. Missing testing helpers

**Core, opt-in files, 1.2:**
- `clicksend/testing/rspec`: `have_sent_sms(**attrs).once/.times(n)` and
  `have_sent_no_sms` over a `FakeAPI`.
- `clicksend/testing/minitest`: `assert_sms_sent(fake, **attrs)`, `assert_no_sms_sent(fake)`.
- FakeAPI `fail_next(:interrupted, processed: true|false)`. It raises
  `Clicksend::Testing::SimulatedInterrupt < Exception` after (or before) processing, the way a
  worker kill does.

**Not in core:**
- No auto-reset hooks. Without a global fake registry there is nothing to reset automatically.
  The 1.3 Rails gem can reset its own `Clicksend::Rails.fake`.
- No ActiveJob test-adapter glue. It already composes (experiment 5).
- No separate `clicksend-rspec` gem. Precedents for keeping test support in the main gem:
  `Sidekiq::Testing`, `ActionMailer::TestHelper`, aws-sdk's `stub_responses: true`.

**Instance doubles vs FakeAPI vs WebMock** (README guidance to add):
- Use `instance_double(Clicksend::Resources::SMS)` only for pure unit tests of orchestration code.
  It skips argument validation and error mapping.
- Use FakeAPI for anything involving errors, ambiguity or models.
- Use WebMock only to test the HTTP stack itself.

### Q7. What would experienced Ruby developers expect?

| Expectation | Verdict | Why |
|---|---|---|
| `Clicksend.configure { … }` | **Reject in core, forever** | A mutable global contradicts the frozen, per-tenant client (`with`). It leaks between tests and threads, and the reference client (Stripe) is moving away from it (F7). `Client.new` already reads `ENV`. Rails users get `config.clicksend` in the companion: boot-time only, and it builds one frozen client |
| Rails credentials auto-loading | Companion (1.3) | `credentials.clicksend.{username,api_key}`, then `ENV`. The aws-sdk-rails precedent. Never in core: the core doesn't know about Rails |
| `config.clicksend` | Companion (1.3) | Standard Railtie idiom |
| ActionMailer-like delivery abstraction | **Reject** | `deliver_later` hides the one decision the app must make (what to do on ambiguity); SMS bodies don't need views, layouts or previews; Noticed already owns multi-channel notifications |
| Noticed delivery method | **Recipe (1.2)**; maybe an upstream PR to Noticed later | ~20 lines: `class DeliveryMethods::Clicksend < ApplicationDeliveryMethod` with `deliver` rescuing ambiguity. Noticed's own Twilio/Vonage methods re-raise and so would duplicate on backend retries (F2). A gem would couple to Noticed's internals |
| Logging via Rails.logger | Already supported (`logger:`); default in the companion | — |
| ActiveSupport::Notifications by default in Rails | Companion default (1.3); 1.2 docs | aws-sdk-rails does the same. Core can't default to it without depending on ActiveSupport |

### Q8. Unnecessary framework coupling

- Any `activesupport`, `railties`, `activejob`, `sidekiq`, `opentelemetry-*` or `rspec` runtime
  dependency in the core gemspec.
- Railties or `ActiveSupport.on_load` hooks in core.
- Patching Faraday to change what other instrumentation sees.
- Gem-owned tables or migrations.
- Auto-installed Sidekiq middleware.
- A global fake registry.
- A Noticed or ActionMailer base class.
- Reading `Rails.application.credentials` from core.
- Making the instrumenter ActiveSupport-specific. The duck-typed `instrument(name, payload)` is
  the right contract.

### Q9. What belongs in core

- The request path, retry safety and ambiguity marking (unchanged).
- The duck-typed instrumenter and logger (unchanged).
- `FakeAPI`, plus the new `:interrupted` failure.
- Opt-in RSpec and Minitest helpers with no dependencies (they `require "rspec/expectations"` or
  `minitest` lazily, only when the file is loaded).
- All framework recipes as documentation: jobs, Sidekiq, Noticed, logging, metrics, `Rails.event`,
  OpenTelemetry warning, multi-tenancy, forking.

## 4. Cross-cutting topics

**Service objects and dependency injection.**
- Inject the narrowest thing, the `sms` resource, with a production default:
  `def initialize(sms: CLICKSEND.sms)`.
- Tests pass `fake.client.sms` or `stub_const("CLICKSEND", fake.client)` (experiment 5).
- An initializer constant (`CLICKSEND = Clicksend::Client.new(...)`) is fine. Zeitwerk doesn't
  reload it, and it shouldn't: it holds no app code.
- `Rails.application.config.x.clicksend_client` works too but adds nothing. Prefer the constant,
  or `Clicksend::Rails.client` in 1.3.
- Never put credentials in job arguments (they are stored in Redis or the database and logged).
  Pass a tenant id.

**Testing doubles.** See Q6. FakeAPI first; instance doubles for orchestration-only unit tests;
WebMock for HTTP-level checks.

**Structured logging.**
- The `logger:` line format stays human-readable.
- For key/value or JSON logs, subscribe to `/\.clicksend\z/` and emit the payload fields (10
  lines; experiment 4, no phone numbers or text).
- semantic_logger users can do this with `SemanticLogger["Clicksend"].info("request", payload)`.
- lograge only shapes controller request logs and is not the right hook.
- On Rails 8.1, the `Rails.event` bridge is the native form.

**Observability (metrics).**
- Tag by `operation` and an outcome:
  `ok | rejected | error | ambiguous` (from `response_code`, `exception`, `ambiguous`), plus the
  `http_status` class.
- **Never tag by `path`.** `/v3/sms/receipts/{message_id}` and `/v3/sms/inbound-read/{id}` give
  unbounded cardinality.
- Recipes for StatsD (`StatsD.distribution`/`increment`), prometheus-client (a `Histogram` and a
  `Counter` with `labels: [:operation, :outcome]`) and Yabeda (a `group :clicksend` with
  `requests_total` and `request_duration`), all from the same subscriber.
- Alert on `ambiguous=true` and on `retry.clicksend` with `error_class=Clicksend::RateLimitError`.

**Multi-tenant and subaccount credentials.**
- `client.with(username:, api_key:)` costs about 49µs and 179 allocations. Build one per job, or
  cache per tenant in a `Concurrent::Map` or a Mutex-guarded Hash for hot paths.
- Rebuild on credential rotation; never mutate.
- Store subaccount keys encrypted (ActiveRecord encryption).
- Instrumentation payloads carry no username. Tenant labels in metrics are the app's choice; add
  them in the subscriber from the app's own context.

**Thread safety.**
- A frozen `Client` is shared across Puma threads and Sidekiq workers.
- FakeAPI is synchronised.
- The one caveat is unchanged: logger and instrumenter subscribers run on the caller's thread and
  must be thread-safe.

**Forking** (Puma cluster `preload_app!`, Sidekiq Enterprise swarm, Rails parallel tests):
- A client built before fork is safe with the default adapter (a connection per request; no
  sockets survive).
- With `net_http_persistent`, connection_pool ≥ 2.4.0 drops pooled connections after fork
  automatically.
- FakeAPI is per-process after fork, which is what parallel test workers want.

## 5. Keep / Change / Add / Reject

**Keep:**
- the frozen per-instance client and `with`;
- the duck-typed instrumenter and logger;
- Faraday as the only runtime dependency;
- FakeAPI as a transport;
- no history in FakeAPI;
- no verification for webhooks.

**Change (docs, 1.2):**
- Rewrite "Background jobs": the timeout budget (F3), declaration order (F1), stacked retry layers
  (F2), the in-flight marker (F4) with tested code, Sidekiq `:kill` and its "Retry Now" hazard.
- Lower the recommended *job* client timeout: `timeout: 10–15` and `max_retry_after: 5`, below the
  runner's grace period. The 30s default stays for interactive use.

**Add (1.2):**
- the `clicksend/testing/rspec` and `clicksend/testing/minitest` helpers;
- FakeAPI `:interrupted`;
- recipes for Noticed, `Rails.event`, structured logs, metrics, and an OpenTelemetry instrumenter
  snippet, with the `url.full` warning.

**Add (1.3, gated on demand):** `clicksend-rails` and `clicksend-opentelemetry`.

**Reject:**
- `Clicksend.configure`;
- ActionMailer-like texters;
- gem-owned ledger tables;
- `clicksend-sidekiq`, `clicksend-rspec`, `clicksend-noticed`;
- an engine with webhook routes;
- monkey-patching;
- making `discard_on`-based recipes the primary advice (order-fragile).

## 7. Item cards

Scale: Low / Medium / High.

### A1. Background-jobs documentation rewrite (core docs)
- **User value:** High. It closes the only duplicate path users hit with the 1.1 recipe (shutdown
  re-runs, experiment 2) and the order trap (experiment 1D).
- **Complexity:** Low. **Maintenance:** Low; re-run the experiments on major Rails or Sidekiq
  releases.
- **API surface:** none. **Dependencies:** none.
- **Security:** it should also tell users not to put credentials or phone numbers in job
  arguments (`log_arguments = false` is already there).
- **Compatibility:** none.
- **Evidence:** experiments 1, 2, 3; Sidekiq `manager.rb#hard_shutdown`; Solid Queue README.
- **Recommendation: 1.2.**

### A2. FakeAPI `fail_next(:interrupted, processed:)` (core)
- **User value:** Medium to high. It makes the at-least-once re-run testable, which is how
  applications would verify their marker.
- **Complexity:** Low; experiment 3's `DyingTransport` is the whole idea.
- **Maintenance:** Low.
- **API surface:** one outcome symbol and `Testing::SimulatedInterrupt < Exception`.
- **Dependencies:** none.
- **Security:** none. It is an `Exception`, not a `StandardError`, so the client never reports it
  as a ClickSend failure. That matches `StubError`.
- **Compatibility:** additive. Test code rescuing `Exception` broadly would catch it, which is
  intended.
- **Evidence:** experiment 3; `Connection#attempt_request` rescues only `StandardError`.
- **Recommendation: 1.2.**

### A3. RSpec matcher and Minitest assertions (core opt-in files)
- **User value:** Medium. Shorter failure output and a Minitest equivalent (experiment 5).
- **Complexity:** Low. **Maintenance:** Low; matchers over `SentMessage` attributes only.
- **API surface:** `have_sent_sms`, `have_sent_no_sms`, `assert_sms_sent`,
  `assert_no_sms_sent`. They match the attributes of `SentMessage`, not request bodies.
- **Dependencies:** none declared; loaded only by explicit `require`.
- **Security:** failure messages print recipients and bodies from *test* data only.
- **Compatibility:** RSpec 3.x (tried in experiment 5). Minitest 5 and 6 still need covering in CI.
- **Evidence:** experiment 5; precedents `Sidekiq::Testing`, `ActionMailer::TestHelper`,
  aws-sdk `stub_responses`.
- **Recommendation: 1.2.**

### A4. Observability recipes, plus the OpenTelemetry `url.full` warning (core docs)
- **User value:** High for production teams. The warning prevents personal data in traces.
- **Complexity:** Low. **Maintenance:** Low to medium; vendor APIs drift.
- **API surface:** none. **Dependencies:** none.
- **Security:** positive. It documents that generic HTTP instrumentation records `q=to:+61…`, and
  how to suppress it: exclude the clicksend client's Faraday connection, or wrap calls in
  `OpenTelemetry::Common::Utilities.untraced` when the dedicated instrumenter is used.
- **Compatibility:** none.
- **Evidence:** experiment 4; `cleanse_url` source.
- **Recommendation: 1.2.**

### A5. Noticed delivery-method recipe (core docs)
- **User value:** Medium. Noticed has about 7M downloads and is the de-facto Rails notifications
  gem.
- **Complexity:** Low. **Maintenance:** Low; it follows Noticed's documented custom delivery-method
  API.
- **API surface:** none. **Dependencies:** none.
- **Security:** same as the job recipe.
- **Compatibility:** Noticed ≥ 2 (delivery methods are jobs).
- **Evidence:** Noticed 3.1.0 source (F2).
- **Recommendation: 1.2.** Consider an upstream Noticed PR later; **never** a gem.

### B1. `clicksend-rails` (companion)
- **User value:** Medium. Enforcement that ignores declaration order (1F) and a boot-time
  timeout-budget warning. The rest is convenience.
- **Complexity:** Medium.
- **Maintenance:** Medium to high. It needs a Rails 7.2/8.0/8.1 matrix and must track ActiveJob
  callbacks, Solid Queue and Sidekiq configuration APIs, and `Rails.event` (8.1+).
- **API surface (new gem):** `config.clicksend`, `Clicksend::Rails.client`,
  `Clicksend::Rails.fake`, `Clicksend::Rails::SendsSms` with `on_ambiguous_sms`, and maybe
  `claim_sms!`.
- **Dependencies:** `railties`, `activejob`; core unchanged.
- **Security:**
  - credentials come only from `credentials`/`ENV` and are never logged;
  - no routes or engine;
  - the hook's default reporting (`Rails.error.report`) must not attach job arguments. They can
    hold phone numbers.
- **Compatibility:** Rails ≥ 7.2 (`rescue_from` with modules is verified back to 7.0; 7.1 is past
  end of life by 2026-10). The `Rails.event` bridge needs 8.1.
- **Evidence:** experiments 1, 2, 4; the aws-sdk-rails precedent.
- **Recommendation: 1.3, gated on demand.** Ship the concern as a README snippet in 1.2 first.

### B2. `clicksend-opentelemetry` (companion)
- **User value:** Medium. One CLIENT span per logical call, named by `operation` (e.g.
  `clicksend sms.deliver`), with:
  - `url.full` without the query;
  - `http.response.status_code`;
  - `clicksend.ambiguous`;
  - retry span events;
  - optionally, the generic Faraday child span suppressed.
- **Complexity:** Medium (parenting, error status, and the decision to suppress the Faraday span).
- **Maintenance:** Medium. OpenTelemetry Ruby is still migrating semantic conventions: the
  installed Faraday instrumentation warns that the old-semconv opt-in "will be removed on April
  15, 2026".
- **API surface:** `Clicksend::OpenTelemetry::Instrumenter.new(tracer_provider:)`, passed as
  `instrumenter:`. It composes with ActiveSupport::Notifications through a small fan-out
  instrumenter (documented, not shipped).
- **Dependencies:** `opentelemetry-api` only (the SDK stays the app's choice).
- **Security:** positive (F5). It must never record bodies, headers, query or `to`.
- **Compatibility:** independent release cadence. Core unchanged.
- **Evidence:** experiment 4; the roadmap's P1 item.
- **Recommendation: 1.3** (moved from the roadmap's 1.2 into its own gem). README snippet in 1.2.

### C1. Global `Clicksend.configure` — **Never**
- **User value:** Low; familiarity only.
- **Complexity:** Low, but it changes the core design.
- **Maintenance:** High. Precedence rules, thread-visibility bugs, test leakage.
- **API surface:** a large implicit one.
- **Dependencies:** none.
- **Security:** negative. Mutable credentials are shared process-wide, and a tenant mix-up becomes
  possible.
- **Compatibility:** confusing next to `with`.
- **Evidence:** F7 (Stripe's move to `StripeClient`); the 1.1 roadmap's rejection.

### C2. ActionMailer-like texter abstraction — **Never**
- **User value:** Low to medium.
- **Complexity:** High. **Maintenance:** High.
- **API surface:** large.
- **Dependencies:** ActionPack/ActiveJob.
- **Security:** negative. `deliver_later` encourages fire-and-forget, so ambiguity goes unhandled.
- **Evidence:** F2; ActionMailer's `MailDeliveryJob` simply delegates exceptions to the mailer.

### C3. Gem-owned send ledger table and migration generator — **Never** in this form
- **User value:** Medium. **Complexity:** Medium. **Maintenance:** High (multi-database, schema

- **Security:** negative if it stores recipients. It is redundant if it doesn't.

- **Alternative:** the `claim_sms!` helper over an app column, possibly in B1.

### C4. `clicksend-sidekiq` — **Never**
- **User value:** Low. One `sidekiq_retry_in` line already works.
- **Maintenance:** Medium.

## 8. API sketches (illustrative only; not implemented)

Job client with a timeout budget (1.2 docs):

```ruby
# config/initializers/clicksend.rb
CLICKSEND = Clicksend::Client.new(logger: Rails.logger, instrumenter: ActiveSupport::Notifications)
# Jobs: one attempt's read timeout must end well inside the runner's shutdown grace period
# (Sidekiq -t 25, Solid Queue shutdown_timeout, Kubernetes terminationGracePeriodSeconds).
CLICKSEND_JOBS = CLICKSEND.with(timeout: 15,
  retry_policy: Clicksend::RetryPolicy.new(max_retries: 1, max_retry_after: 5))
```

In-flight marker on the application's row (1.2 docs; experiment 3):

```ruby
class SendNotificationSmsJob < ApplicationJob
  self.log_arguments = false

  def perform(notification_id)
    claimed = Notification.where(id: notification_id, sms_state: "pending")
      .update_all(sms_state: "sending", sms_claimed_at: Time.current) == 1 # committed before the call
    unless claimed # already sent, or a previous run died mid-send ("sending"): never send again
      ReconcileSmsJob.perform_later(notification_id) if Notification.exists?(id: notification_id, sms_state: "sending")
      return
    end

    n = Notification.find(notification_id)
    message = CLICKSEND_JOBS.sms.deliver(to: n.phone, body: n.text, custom_string: "notification:#{n.id}")
    n.update_columns(sms_state: "sent", sms_message_id: message.message_id)
  rescue Clicksend::AmbiguousRequestError
    Notification.where(id: notification_id).update_all(sms_state: "unknown")
    ReconcileSmsJob.perform_later(notification_id)
  rescue Clicksend::MessageRejected
    Notification.where(id: notification_id).update_all(sms_state: "failed")
  rescue Clicksend::Error
    Notification.where(id: notification_id, sms_state: "sending").update_all(sms_state: "pending")
    raise # not processed: let retry_on / the backend retry
  end
end
```

(The rescue clauses that write to the database can themselves fail. When they do, the row stays
`sending`, and the next run reconciles instead of sending. That is the safe direction.)

Sidekiq safety net (1.2 docs; experiment 2):

```ruby
class SmsJob
  include Sidekiq::Job
  # Belt and braces: if an ambiguous error ever escapes perform, park it in the Dead set
  # (do not press "Retry Now" there without reconciling first).
  sidekiq_retry_in { |_count, error, _job| :kill if error.is_a?(Clicksend::AmbiguousRequestError) }
end
```

Noticed delivery method (1.2 docs):

class DeliveryMethods::Clicksend < ApplicationDeliveryMethod

    CLICKSEND_JOBS.sms.deliver(to: recipient.phone_number, body: params.fetch(:message),
      custom_string: "noticed:#{notification.id}")

## 9. What would change these recommendations

- **ClickSend adds an idempotency key.** Then the core should send one on every `deliver`, and most
  of sections 3 and 4 shrink to "retries are safe" (as with Stripe).
- **Strong demand for Rails conveniences.** Then `clicksend-rails` moves to 1.2.x; the README
  snippets make the API easy to lift.
- **OpenTelemetry HTTP semantic conventions stabilise and the Faraday instrumentation gains query
  redaction.** Then B2 shrinks to documentation.
- **Solid Queue or Sidekiq add a "do not requeue on shutdown" job option.** Then the timeout
  budget becomes optional advice.
