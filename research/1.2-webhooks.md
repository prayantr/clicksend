# 1.2 spike: webhook evolution

Branch `spike/1.2-webhooks`, from the 1.1.0 release commit `7e96b24`. Researched 2026-10-06.
No ClickSend API call was made, and no ClickSend test-push endpoint was used.

`Clicksend::Webhook` shipped in 1.1 as *experimental*, because ClickSend's current docs define no
push payload and no push had been captured. This spike looked for better evidence, built a way to
make webhook changes safe once real pushes are captured, and proposes what 1.2 should do.

## Summary

New since the 1.1 research:

1. **The pushed field lists exist, in archived ClickSend help.** "What DLR format will the API
   send?" lists the keys of the inbound and the delivery-receipt push, including legacy
   duplicates (`message`, `sms`, `originalsenderid`, `originalmessage`, `originalmessageid`,
   `customstring`, `messageid`) that 1.1 didn't know about. Two ClickSend-published integrations
   (the n8n trigger and the Power Automate connector) show the same core keys and some of the
   duplicates for JSON pushes, with JSON integers for `user_id`, `subaccount_id` and (in n8n's example) `timestamp`.
2. **1.1 overstated the absence of security guidance.** It said no current, archived or help
   source mentioned IP ranges. Archived help did: a security article (HTTPS, a URL token, checking
   `user_id`, checking the source IP) and a list of six source IPs last updated around 2019. Neither
   is published now. This doesn't change the design (nothing can be verified
   cryptographically), but the docs were wrong and are corrected on this branch.
3. **Archived sources disagree on retries.** The 2022 REST v3 docs say every 10 minutes, 10 times,
   with a 30 s timeout. A help article updated around 2022 says backoff (10 s, 1 min, 5 min, 30 min, 1 h, ...)
   "over a long period (hours)", with a 15 s timeout. Nothing current says either.
4. **Receipts may not be unique per message** (pending codes "can update at any time"; inferred).
   Deduplicating receipts on `message_id` alone, as the 1.1 README advised, could then drop a
   final receipt after a pending one. Corrected.
5. **A free way to capture a push exists.** The dashboard's "Add Test Reply" button on a rule
   posts an example to the rule's URL (current help for Make, and archived troubleshooting help).
   No SMS is sent and no API credentials are needed.
6. Nothing found contradicts what `Clicksend::Webhook` parses today. Every published shape replays
   green through the gem (see the prototype).

Recommendation: ship the documentation corrections and the replay tooling in 1.2 with no change to
the `Webhook` API; have the owner capture real pushes with the protocol below; remove the
experimental label only after the captures replay green (1.3 at the earliest).

### 1.3 What is still unknown

Only a capture can answer these: the exact current key set and order for each `webhook_type`; JSON
Content-Type; null encoding; whether receipts carry the legacy duplicates today; whether pending
receipts (200, 300) are pushed at all; current retry schedule and timeout; current headers and

## 2. Prototype: replay fixtures and capture tooling

On this branch:

- `spec/fixtures/webhooks/`: one file per published push shape, in `archived/`, `first_party/`,
  `documented/` and `synthetic/`, plus an empty `captured/`. `.form`, `.query` and `.json` files
  hold a body or query string; `.http` files hold a raw request. `manifest.yml` gives each one a
  kind, label, source, note, and the model attributes and `raw` entries it must produce. Values
  are made up; phone numbers are ClickSend test numbers.
- `spec/support/webhook_replay.rb`: builds a Rack request from a fixture with
  `Rack::MockRequest.env_for`, then extracts params the way an app does (`request.GET`,
  `request.POST`, or `JSON.parse` of the body), and simulates Rails' ParamsWrapper for JSON.
- `spec/clicksend/webhook_replay_spec.rb`: for every manifest entry, parses with the specific
  method and with `Webhook.parse`, checks attributes and `raw`, and checks the ParamsWrapper
  variant. Hygiene checks fail the suite if a fixture is missing from the manifest, contains a
  phone number other than a ClickSend test number, carries a token in its request line, or keeps
  the value of a header outside a short allowlist.
- `script/webhook_capture.rb` (standard library only, not shipped in the gem):
  - `serve` listens on 127.0.0.1 behind a tunnel, saves only requests under `/<secret>/` (mode
    0600, secret replaced by `:secret`, also in headers), answers 200 at once (or a chosen status,
    to watch retries), rejects bodies over 64 KB and chunked bodies, and stops after 20 captures.
  - `redact` rewrites a capture into a fixture: phone numbers to test numbers (equal numbers stay
    equal), text to placeholders (URLs stay URLs), IDs to same-shaped fakes, account IDs to
    100001/100002, header values outside the allowlist to `[redacted]`. Key names, order, value
    types, empty values and timestamps are kept, because they are the evidence. Unknown keys are
    kept and reported, with number-like substrings replaced.
- `spec/script/webhook_capture_spec.rb` covers both commands, including over a real socket.

All seven published shapes parse correctly with 1.1's code, so nothing in `lib/` needed to change.

**Why Rack as a development dependency.** The point of a replay is to see the params an app sees,
and Rack's parser decides them: UTF-8 tagging, last-wins for repeated keys, and nested Hashes for
`a[b]` keys, all of which `Webhook` has rules for. Re-implementing that with
`URI.decode_www_form` would test our idea of Rack instead of Rack. Rack is already present in
every Rails or Sinatra app this gem targets, is maintained, and is `require: false` in the root
Gemfile (like `activesupport`), so it never reaches the gem's runtime dependencies (still Faraday
only). Note for the owner: this worktree's `vendor/bundle` is the same directory as the frozen
checkout's, so `bundle install` added `rack-3.2.7` there; that checkout's Gemfile.lock and tracked
files are untouched.

## 3. Capture protocol (for the owner)

Goal: one redacted real push per shape, replayed in CI. Do it from your own account; nothing here
was or should be run by an agent.

**What it costs.**
- Inbound and receipt test pushes from the dashboard ("Add Test Reply"): free, no SMS.
- The test-push API endpoints (`POST /v3/sms/inbound`, `POST /v3/sms/receipts`) need API
  credentials and push to any URL you give them; ClickSend doesn't say whether they cost anything.
- A **real receipt** needs a real SMS to a real phone, charged at your rate: test numbers produce
  no delivery report (legacy v2 docs, and the 1.1 live run saw none).
- A **real inbound** needs someone to text your number: reply from your own phone to that SMS
  (a reply to a shared number), or text a dedicated number (a monthly fee). Use only phones you
  own: a capture of someone else's message is their personal data.

**Setup.**
1. `export CLICKSEND_CAPTURE_SECRET=$(ruby -rsecurerandom -e 'puts SecureRandom.urlsafe_base64(24)')`
2. `ruby script/webhook_capture.rb serve` (port 9292; saves to `tmp/webhook-captures/`, which git ignores).
3. Start a tunnel with a public certificate (ClickSend requires a valid chain), for example
   `cloudflared tunnel --url http://127.0.0.1:9292`. TLS ends at the tunnel provider, which can
   read the traffic: fine for test pushes; for real messages, decide whether you accept that.
   Avoid public request bins for real messages for the same reason.
4. The rule URL is `https://<tunnel-host>/<secret>/<name>`, where `<name>` says what it is, e.g.
   `inbound-post`, `inbound-json`, `inbound-get`, `receipt`. Use a path secret, not `?token=`.

**Captures, cheapest first.**
1. Inbound rule, action URL, default format → **Add Test Reply**. Then the same with
   `webhook_type` `json` and `get` (if the dashboard doesn't offer them, set them with
   `client.request(:put, "/v3/automations/sms/inbound/<id>", body: {...})` yourself).
2. Delivery-report rule, action URL → **Add Test Reply**, if the button is there.
3. Optional, paid: send one SMS to your own phone with the receipt rule active; wait for the
   delivered receipt (seconds to hours). Reply from that phone to capture a real inbound.
4. Optional, to measure retries: restart with `CAPTURE_STATUS="500 Internal Server Error"` and
   trigger one test push; the saved files' timestamps show the schedule. Disable the rule after an
   hour or two, or the retries continue.
5. Optional: to learn whether pending receipts are pushed, keep the receipt rule active while
   sending to a phone that is switched off (a 300 then a final code, if ClickSend pushes both).

**Redact and commit.**
1. `ruby script/webhook_capture.rb redact tmp/webhook-captures/<file>.http spec/fixtures/webhooks/captured/<name>.http`
2. Read the `check:` lines and then the whole output file. Unknown keys are kept: make sure none
   holds personal data.
3. Add an entry to `manifest.yml`: `label: captured`, `source` (e.g. `capture 2026-10-20,
   inbound rule, webhook_type json, Add Test Reply`), a note, and the expected attributes.
4. `bundle exec rspec spec/clicksend/webhook_replay_spec.rb`.
5. Record in `docs/clicksend-api-notes.md`: method, Content-Type, keys, types, null encoding,
   `User-Agent`, and the source IP (it was in `X-Forwarded-For` or `Cf-Connecting-Ip` in the raw
   capture; compare with the archived list, but don't commit it as an allowlist).
6. Clean up: delete or disable the capture rules, stop the tunnel and the server, and delete
   `tmp/webhook-captures/` (it holds unredacted data).

## 4. Receiver pattern (Rails)

The gem's part stays small: parse a Hash into a frozen model, reject junk. The rest belongs in the
app, and the README now shows it:

1. **Route with a path secret**, compared with `secure_compare`; to rotate, accept the old and the
   new secret until every rule uses the new URL. Rails 8.1 logs the request path unfiltered (it
   filters query parameters only, R1), so restrict log access; proxies keep full URLs anyway. A
   query token (`?token=`) is filtered in Rails' log but merges into a `get` rule's parameters.
2. **Parse `request.request_parameters`** (body only, so the secret stays out of `raw`); for a `get`
   rule, `request.query_parameters`. ParamsWrapper's nested copy for JSON is ignored (1.1 fix).
3. **Answer 200 within a few seconds** (A5: 15 s timeout) and enqueue a job with the
   `message_id` (and for receipts the status code), not the payload, so job logs hold no personal
   data. Answer 400 on `InvalidPayload`; ClickSend will probably retry it (any non-200 is
   retried), which is noise, not harm.
4. **Idempotency.** Inbound: a unique index on `message_id`. Receipts: one row per message,
   updated only when the new status is final or the stored one is pending (README snippet). Both
   are order-independent.
5. **Confirm before acting** when it matters: `client.sms.receipt(message_id)` for receipts (still
   unverified for URL-only accounts); there is no fetch-by-ID for inbound.
6. **Filter parameters**: `body`, `message`, `from`, `to`, `sms`, `originalsenderid`,
   `original_body`, `originalmessage`. Rails' default filters cover `secret` and `token`, but none
   of these.
7. In a job that parses or confirms, `discard_on Clicksend::Webhook::InvalidPayload` below
   `retry_on Clicksend::Error`.

**A `Deduplicator` in the gem: rejected.** Correct deduplication needs durable shared storage (a
database unique index or an atomic cache write), and the right key differs by event (inbound by
`message_id`; receipts by message with "final wins"). Anything in core would either couple the gem
to a framework or store state in memory, which fails across processes and restarts. The README
recipe (about ten lines) is the right size.

## 5. API refinements considered

| Proposal | Decision | Reasoning |
|---|---|---|
| Separate base class for `InvalidPayload`, so `retry_on Clicksend::Error` doesn't retry bad payloads | **Reject**; document `discard_on` | Usually the controller parses, not a job. Leaving `Clicksend::Error` breaks the README's "every error is a `Clicksend::Error`" and existing `rescue Clicksend::Error`. A one-line `discard_on` solves the job case. `retryable?` is already false |
| Drop or rename `Webhook.parse` | **Keep** | A2 shows disjoint key sets (`status_code` only on receipts, `body`/`from` only on inbound), so detection is sound for every published shape, and it is handy behind one URL or for Add Test Reply |
| Read the legacy duplicates as fallbacks (`message` for `body`, `messageid` for `message_id`) | **Reject for now** | No source shows the primary keys missing; fallbacks add precedence questions. Revisit if a capture shows otherwise |
| Treat `""` as nil for optional fields of form pushes | **Defer to 1.3** | Form encoding can't tell null from empty, but ClickSend's own poll schema returns `""` for an inbound `custom_string`, so a change would make push and poll differ. Decide with captures |
| `Webhook.params_from(rack_request)`: pick GET/form/JSON by method and Content-Type | **1.3, if captures confirm the JSON Content-Type** | Saves non-Rails users a branch; Rails' `request_parameters` already does it. Duck-typed, no dependency. The replay helper is the prototype |
| `user_id:` check in the parsers | **Reject as an API**; mention in docs only if asked | `user_id` is in every push, so it is not a secret (A3 calls it a check, not authentication). One line in the app if wanted |
| Reject receipts whose `message_type` isn't SMS | **Reject**; document | MMS's value is unknown; rejecting would lose data. The model exposes `message_type` |
| Verify source IPs | **Reject** | Stale archived list (A4); wrong IPs silently drop real pushes |
